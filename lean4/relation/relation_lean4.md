## 블록 1 — `import Mathlib`

```lean
import Mathlib
```

`import` — 영어 단어 그대로 "수입하다, 가져오다". 다른 파일에서 미리 만들어 둔 도구를 우리 파일로 끌어오는 명령. Python 의 `import`, C 의 `#include`, JavaScript 의 `import` 와 같은 역할. 다른 언어를 배운 적 있는 분은 친숙할 거예요.

### `Mathlib`

Lean 4 의 거대한 수학 라이브러리. 수학 도서관 (Mathematical library) 의 줄임말이다. 자연수의 덧셈 정리부터 위상수학, 대수기하학까지 — 수학의 거의 모든 영역의 정의와 정리. 2026 년 현재 약 100 만 줄.

## 블록 2 — 곱 타입과 순서쌍 정의

```lean
-- A × B 는 곱 타입. (a, b) 는 그 타입의 값이다.
def p : Nat × Nat := (3, 5)
```

먼저 첫 줄 `-- A × B 는 곱 타입. (a, b) 는 그 타입의 값.`.

두 개의 빼기 부호 `--` 는 Lean 4 의 주석 (comment) 기호이다.

둘째 줄 `def p : Nat × Nat := (3, 5)`.

`def` — 영어 단어 "define" 의 약자. "정의한다" 라는 뜻. 다음에 오는 `p` 가 새 이름이다.

비유 — 변수에 값을 넣는 것 같지만, 더 정확히는 "이름이 이 값을 가리키도록 약속" 하는 것이다.

`p` — 우리가 새로 만드는 이름. 아무 이름이든 가능하다. `a`, `myPoint`, `학생` 도 가능. 한글도 된다.

`: Nat × Nat` — 타입 표기. 두 부분으로 나뉜다.

`:` — 콜론. "다음에 오는 게 이 이름의 타입이다" 라는 뜻. 수학 표기 `p ∈ A` 와 비슷한 의미. "p 가 어떤 종류의 객체인지" 알려 주는 표시이다.

`Nat` — Natural number 의 약자. 자연수의 타입. Lean 4 에서는 0, 1, 2, 3, ... 모두 자연수이며 0 도 포함한다. (이건 학파에 따라 다른데 Lean 은 0 포함파이다.)

`×` — 키보드의 X 가 아니라 유니코드 곱셈 기호. 두 타입을 합쳐 곱 타입 (product type) 을 만드는 연산자. 수학의 곱집합 $A \times B$ 와 정확히 같다.

`Nat × Nat` 의 의미 — "두 자연수의 곱집합 타입" 또는 "두 자연수의 쌍을 담는 타입". 수학 표기로 $\mathbb{N} \times \mathbb{N}$.

`\times` 를 치고 스페이스나 탭을 누르면 `×` 로 변환된다. 또는 `\x` 도 가능하다. 비슷한 패턴으로 `\to` 가 `→`, `\and` 가 `∧`, `\or` 가 `∨` 이다.

`:=` — 콜론 더하기 등호. "이 값이다" 라는 할당. `p : Nat × Nat := (3, 5)` 는 "p 는 자연수 두 개의 쌍이고, 그 값이 $(3, 5)$" 라는 한 줄의 약속이다.

`(3, 5)` — 순서쌍 (ordered pair) 표기. 수학에서 적는 그대로. 첫 자리에 3, 둘째 자리에 5.

Lean 4 가 `(3, 5)` 를 받으면 `Prod.mk 3 5` 라는 함수 호출로 해석한다. `Prod` 는 곱 타입의 이름, `mk` 는 "make (만들다)" 의 줄임말, 곧 곱 타입의 값을 만드는 생성자이다.

```lean
-- 곱 타입은 세 개 이상으로도 중첩된다: Nat × Nat × Nat
def t : Nat × Nat × Nat := (3, 4, 27)
```

세 자연수의 쌍. `Nat × Nat × Nat` 는 세 자연수의 곱 타입이며 값은 `(3, 4, 27)`. 세 자리 각각 3, 4, 27 이다.

`Nat × Nat × Nat` 가 내부에서 `Nat × (Nat × Nat)` 로 해석된다. 결과적으로 `(3, 4, 27)` 이 내부에서 `(3, (4, 27))` — 중첩된 두 순서쌍이 된다.

## 블록 3 — `.1`, `.2` 점 표기와 `rfl`

```lean
-- .1 은 첫째 성분, .2 는 둘째 성분을 꺼낸다.
example : p.1 = 3 := rfl
example : p.2 = 5 := rfl
```

`example` — 영어 단어 그대로 "예시". 이름 없는 정리이다. `def` 는 새 이름을 만들지만 `example` 은 이름 없이 그저 "이런 명제가 참" 임을 증명하고 끝난다. 학습용·시범용이다.

언제 example 을 쓰는가 — 시범용일 때. 언제 def 를 쓰는가 — 나중에 재사용할 정리를 만들 때.

우리가 앞서 정의한 `p` 에 점 (`.`) 을 찍고 숫자 1 을 붙였다. 의미는 "p 의 첫째 성분".

`p` 는 `(3, 5)` 라는 순서쌍. `p.1` 은 그 첫 자리, 곧 `3`. `p.2` 는 둘째 자리, 곧 `5`.

Lean 4 의 곱 타입 `Prod` 는 1 부터 시작한다. "첫째 성분", "둘째 성분" 이라 1 부터 센다.

`.fst` 는 First (첫째), `.snd` 는 Second (둘째) 도 가능하다. `p.fst` 는 `p.1` 과 같고 `p.snd` 는 `p.2` 와 같다.

`: p.1 = 3` 부분.

`:` — 다시 콜론. 이번에는 example 의 결론을 가리킨다. "이 example 이 증명하는 명제는 `p.1 = 3` 이다" 라는 뜻.

`p.1 = 3` — 우리가 증명할 명제. "p 의 첫째 성분이 3 과 같다". 수학에서 적는 등식과 같다.

`= 3` 의 `=` 은 일상에서는 등호인데 Lean 4 에서는 "두 값이 같다" 라는 명제이다. 결과는 참 또는 거짓. 곧 `p.1 = 3` 자체가 명제이며 참 명제이면 증명 가능, 거짓이면 불가능하다.

`:= rfl` — 증명. 이게 가장 중요하다.

`rfl` — 영어 단어 reflexivity (반사성) 의 줄임. 한국어로 "반사성", 약어 "rfl", 진술 "모든 객체는 자기 자신과 같다". 곧 임의의 $x$ 에 대해 $x = x$ 가 항상 참이라는 가장 기본적인 등식 사실이다.

`rfl` 이 어떻게 `p.1 = 3` 을 증명하는가. 좌변 `p.1` 을 평가하면 `(3, 5).1` 이 되고, 다시 평가하면 `3`. 우변은 `3`. 좌변과 우변 모두 `3` 으로 환원되었으니 글자 그대로 같다. `rfl` 이 통과한다.

이게 정의 등치 (definitional equality) 라는 개념이다. 영어 그대로 "정의에 의한 동등". 양변이 컴퓨터가 계산만 해서 글자 그대로 같아지면 `rfl` 한 줄로 증명이 끝난다.

수학 표기와 Lean 4 표기의 대응을 표로 정리한다.

| 수학 | Lean 4 |
|---|---|
| $p = (3, 5)$ | `def p : Nat × Nat := (3, 5)` |
| 첫째 성분 | `p.1` |
| 둘째 성분 | `p.2` |
| $x = x$ 의 자명함 | `rfl` |

다음 블록으로.

## 블록 4 — 순서쌍 상등 정리 (`Prod.mk.injEq`)

```lean
example (a c b d : Nat) :
    ((a, b) = (c, d))
      ↔ (a = c ∧ b = d) := by
  -- 정의에 해당하는 정리로 재서술
  rw [Prod.mk.injEq]
```

`example (a c b d : Nat)` —

`(a c b d : Nat)` — 괄호 안에 네 개의 이름과 한 번의 타입 표기. 의미는 "a, b, c, d 네 개가 자연수다." 한 번에 네 변수의 타입을 적은 줄임 표기이다.

수학적으로 "임의의 자연수 a, b, c, d 에 대해" 라는 의미. 이 example 은 모든 자연수 조합에 대해 성립할 명제를 증명할 예정이다.

다음 줄 `: ((a, b) = (c, d)) ↔ (a = c ∧ b = d) := by`.

`((a, b) = (c, d))` — 두 순서쌍의 상등. 좌변 순서쌍 $(a, b)$ 와 우변 순서쌍 $(c, d)$ 가 같다는 명제이다.

`↔` — 새 기호. 양방향 화살표. 영어로 "if and only if", 줄임 "iff", 한국어로 "필요충분조건" 또는 "동치". 진술은 "양쪽이 동시에 참이거나 동시에 거짓". 키보드 입력은 `\iff` 또는 `\<->` 를 치고 스페이스. 수학에서 자주 보는 그 기호이며 $A \iff B$ 와 같다.

`(a = c ∧ b = d)` — 두 등식의 합접.

`∧` — 새 기호. AND, 그리고. 두 명제가 동시에 참. 키보드 `\and` 또는 `\wedge`. `a = c ∧ b = d` 의 의미는 "a 가 c 와 같고 동시에 b 가 d 와 같다".

전체 명제 — "두 순서쌍이 같다 ↔ 첫째 성분이 같고 둘째 성분이 같다." 수학에서 배운 순서쌍 상등의 정의 그대로이며 relation 의 핵심 정리 중 하나이다.

`:= by` — 이번엔 `:= rfl` 이 아니라 `:= by` 로 시작한다.

`by` — 영어 단어 그대로 "by ~으로". 전술 모드 (tactic mode) 의 진입 키워드이다.

전술 모드 — 영어로 tactic mode. 증명을 한 번에 적지 않고 단계적으로 만들어 가는 방식이다. 마치 칠판에 한 줄씩 적으며 증명하는 것처럼. Lean 4 의 가장 자주 쓰는 증명 방식이다.

대조로 직접 모드 (term mode) 가 있다. 증명을 한 줄에 함수처럼 적는 방식. 짧은 증명에 적합하며 블록 3 의 `:= rfl` 이 그 예이다.

`:= by` 다음에는 전술들의 나열이 온다. 한 줄에 하나씩.

`-- 정의에 해당하는 정리로 재서술` — 주석. 사람이 읽으라고 적은 메모. 다음 줄의 의도를 설명한다.

`rw [Prod.mk.injEq]` — 증명의 본체. 한 줄이다.

`rw` — 영어 단어 rewrite (다시 쓰다) 의 줄임. 한국어로 "재작성", 약어 "rw", 진술 "정리를 사용해 목표나 가설을 다시 쓴다".

`rw [정리이름]` 가 작동하는 방식 — Lean 4 가 주어진 정리의 좌변과 일치하는 부분을 목표에서 찾아 우변으로 치환한다. 또는 동치 정리라면 두 형태가 호환된다.

`Prod.mk.injEq` — 정리의 이름. 세 부분으로 나뉜다. `Prod` 는 곱 타입의 이름. `mk` 는 Make (만들다) 의 줄임으로 곱 타입의 생성자. `injEq` 는 Injection equality (단사 등식) 의 줄임으로 "생성자가 단사 함수이므로 등식이 성분별로 분해된다" 는 정리이다.

전체는 "Prod 타입의 mk 생성자의 단사성 등식". 시그너처 (정리의 모양) 가 정확히 다음과 같다.

```
Prod.mk.injEq : ((a, b) = (c, d)) ↔ (a = c ∧ b = d)
```

그래서 `rw [Prod.mk.injEq]` 한 줄로 닫힌다. `rw` 가 목표 `((a, b) = (c, d)) ↔ (a = c ∧ b = d)` 의 좌변과 `Prod.mk.injEq` 의 좌변을 비교하면 같다. 우변으로 치환하면 우리 목표의 우변과 일치한다. 양변 일치로 자동 닫힌다.

InfoView 변화 — 화면 오른쪽의 정보 창에서 보이는 변화이다. 전에는 목표 `((a, b) = (c, d)) ↔ (a = c ∧ b = d)`, 후에는 `No goals` (목표 없음). 한 줄로 끝난다.

## 블록 5 — 예제 5-2 방정식 풀이

```lean
example (x y : Int)
    (h : ((2*x + 1, (5:Int)) = (7, y + 3))) :
    x = 3 ∧ y = 2 := by
  -- (1) 순서쌍 상등으로 성분별 등식 두 개를 얻는다
  rw [Prod.mk.injEq] at h
  -- 이제 h : 2*x + 1 = 7 ∧ 5 = y + 3
  obtain ⟨h1, h2⟩ := h
  -- (2) 각 성분의 결론을 산술로 닫는다
  constructor
  · omega
  · omega
```

`example (x y : Int)` — 두 변수 x, y 가 정수.

`Int` — Integer (정수) 의 줄임. 자연수 `Nat` 와 다른 타입. Lean 4 에서는 0, 음수, 양수 모두 포함하는 정수 타입이다.

**`Nat` 가 아니라 `Int` 인 이유.** 예제의 답을 보면 y = 2 인데, 정수 풀이에서는 음수 답이 나올 가능성도 있다. `Nat` 는 음수가 안 되므로 더 일반적인 `Int` 를 쓴다. 또 산술 풀이에 자유로움을 주기 위해서이다.

`(h : ((2*x + 1, (5:Int)) = (7, y + 3)))` — 가설.

`h` — 가설의 이름. h 는 hypothesis (가설) 의 줄임. 관습적으로 가설은 `h`, `h1`, `h2`, `hab` 같이 짓는다.

`:` 다음은 가설의 내용 `((2*x + 1, (5:Int)) = (7, y + 3))`. 두 순서쌍이 같다는 가정이다.

여기 `(5:Int)` 에 주목한다. Lean 4 에서 숫자 리터럴 `5` 는 문맥에 따라 자연수일 수도, 정수일 수도, 실수일 수도 있다. 타입 추론기가 문맥을 보고 결정한다. 그런데 순서쌍 `(2*x + 1, 5)` 와 `(7, y + 3)` 에서 `2*x + 1` 이 정수 (x 가 정수니까), `y + 3` 도 정수 (y 가 정수니까) 이다. 따라서 둘째 자리의 `5` 도 정수여야 양변 타입이 일치한다.

만약 `:Int` 를 안 적으면 Lean 4 가 자연수로 추론할 수도 있고, 그러면 타입 충돌로 컴파일 오류가 난다. 그래서 명시적으로 `(5:Int)` 라고 적는다.

**헷갈리는 부분** — "5 는 그냥 5 아닌가? 왜 타입을 명시?" 라는 의문. Lean 4 가 다양한 수 체계를 다루므로 정확한 타입을 알려야 한다. 작은 불편이지만 안전을 위한 것이다.

`: x = 3 ∧ y = 2` — 결론. "x 가 3 이고 y 가 2". 합접이다.

`:= by` — 전술 모드 진입. 익숙해진 그것이다.

이제 본격 증명. 네 줄이다.

`rw [Prod.mk.injEq] at h` — 블록 4 에서 본 `rw [Prod.mk.injEq]` 와 비슷한데 끝에 `at h` 가 추가되었다.

`at h` — "h 라는 위치에서". 곧 `rw` 를 목표에서가 아니라 가설 h 에서 적용한다. 블록 4 의 `rw [Prod.mk.injEq]` 는 목표를 다시 쓰고, 여기의 `rw [Prod.mk.injEq] at h` 는 가설 h 를 다시 쓴다.

방향은 Lean 4 가 자동 처리한다. 가설이 순서쌍 등식 형태이므로 성분별 등식의 합접으로 변환된다.

InfoView 변화 — 전에는 `h : (2*x + 1, 5) = (7, y + 3)`, 후에는 `h : 2*x + 1 = 7 ∧ 5 = y + 3`. 가설이 합접으로 변환된다.

`obtain ⟨h1, h2⟩ := h` — 다음 전술.

`obtain` — 영어 단어 그대로 "얻다, 입수하다". 복합 명제를 분해해 작은 가설들을 얻는 전술이다.

`⟨h1, h2⟩` — 꺽쇠 표기. 새 기호이다. `⟨` 와 `⟩` 가 일반 괄호 `<>` 와 비슷하지만 다른 기호이다. 키보드 `\<` 와 `\>`, 또는 `\langle` 와 `\rangle`. 꺽쇠의 의미는 안에 든 것을 그 자리에서 분해 또는 묶음. 여기서는 분해이다.

`obtain ⟨h1, h2⟩ := h` 가 하는 일 — h 가 합접 `A ∧ B` 형태일 때, h 를 두 부분 `h1 : A` 와 `h2 : B` 로 분해한다. 원래 `h` 는 사라지고 두 새 가설이 등장한다.

InfoView 변화 — 전에는 `h : 2*x + 1 = 7 ∧ 5 = y + 3`, 후에는 `h1 : 2*x + 1 = 7`, `h2 : 5 = y + 3`. 합접이 두 가설로 풀린다.

학생들이 자주 묻는 의문 — "꺽쇠 안에 이름이 두 개인 이유는?" 분해된 두 부분에 각각 이름을 붙이려는 것이다. h1 이 첫째 부분, h2 가 둘째 부분. 이름은 자유이며 h1, h2 대신 left, right 같은 이름도 가능하다. 관습적으로 h1, h2 를 쓴다.

### 다음 줄 `constructor`

`constructor` — 영어 단어 그대로 "생성자". 결론이 합접일 때 그 합접의 생성자를 적용해 두 부 목표로 분해한다.

`obtain` 과 `constructor` 의 차이를 짚는다. `obtain ⟨...⟩ := h` 는 가설의 합접을 분해하고, `constructor` 는 목표의 합접을 분해한다. 대칭적인 두 전술이며 가설과 목표 양쪽에서 합접을 다루는 도구이다.

InfoView 변화 — 전에는 목표 `x = 3 ∧ y = 2`, 후에는 두 부 목표 (1) `x = 3`, (2) `y = 2`. 한 목표가 둘로 나뉜다.

수학에서 "A 그리고 B 를 보이려면 A 를 보이고 또 B 를 보인다" 의 정확한 대응이다. 목표를 둘로 나눠 각각 따로 증명한다.

다음 줄 `· omega`.

`·` — 가운데 점 (centered dot). 키보드 입력 `\.` 또는 `\cdot`. 자주 쓰는 기호이다. 의미는 부 목표 시작 표시. `constructor` 가 두 부 목표를 만들었으므로 각각에 대해 `·` 로 시작해 증명을 분리해 적는다.

`omega` — 새 전술. 영어로 "omega", 한국어로도 "오메가". 약어가 아닌 그리스 문자 이름 그대로. 진술은 "선형 정수 산술 (linear integer arithmetic) 의 결정 알고리즘".

**선형 정수 산술** — 덧셈, 뺄셈, 상수와 변수의 곱, 부등식, 등식만으로 표현되는 정수 식. 변수 두 개의 곱 (예 x · y) 같은 비선형은 제외된다.

**omega 가 하는 일** — 가설과 목표를 종합해 자동으로 산술적 결론을 도출한다. 1990 년대 William Pugh 가 도입한 알고리즘이며 Lean 4 의 Mathlib 가 그 구현체이다.

첫 부 목표는 `x = 3`. 사용 가능한 가설은 `h1 : 2*x + 1 = 7`. omega 가 `h1` 을 사용해 `2*x = 6` 에서 `x = 3` 을 자동 유도한다. 부 목표가 닫힌다.

둘째 부 목표 `· omega` 는 같은 일을 둘째 부 목표 `y = 2` 에 대해 한다. 가설 `h2 : 5 = y + 3` 에서 `omega` 가 `y = 2` 를 도출한다.

### omega 가 무엇이든 자동 풀어 주는가

선형 정수 산술만 처리한다. 비선형 (`x * y` 같은 두 변수의 곱) 은 불가능하다. 그때는 `nlinarith` (nonlinear linear arithmetic) 같은 다른 전술이 필요하다. 우리 예제는 완전히 선형이라 `omega` 가 즉시 해결한다.

### 왜 `omega` 가 그렇게 강력한가

선형 정수 산술이 결정 가능 (decidable) 하기 때문이다. 곧 모든 참 명제를 알고리즘이 항상 찾아낼 수 있는 영역이다. 1929 년 Mojzesz Presburger 가 증명했다. omega 가 그 결정 알고리즘의 구현이다. 수학자가 손으로 푸는 모든 선형 부등식 사슬을 0.1 초에 처리하는 자동화의 정점이다.

## 수학 풀이와 Lean 4 코드의 1:1 대응

| 수학 풀이 | Lean 4 코드 |
|---|---|
| "순서쌍 상등을 풀어 쓰면" | `rw [Prod.mk.injEq] at h` |
| "첫 성분 등식과 둘째 성분 등식" | `obtain ⟨h1, h2⟩ := h` |
| "결론도 두 부분으로 나누어" | `constructor` |
| "첫째에서 x = 3" | `· omega` |
| "둘째에서 y = 2" | `· omega` |

수학의 다섯 단계가 코드의 다섯 줄. 형식 증명의 미이다.

또 의문 — "두 부 목표 모두 omega 인데, 한 번에 처리할 수 없나요?" 가능하다. `<;> omega` 라는 단축 표기가 있다. 세미콜론 두 개가 "모든 부 목표에 같은 전술 적용" 을 뜻한다. 그러나 명시성을 위해 두 번 따로 적었다. 학습 단계에서는 명시가 좋다.

## 블록 6 — 관계 정의 `Le`

```lean
-- 관계: 두 인수를 받아 명제를 돌려주는 함수
def Le : Nat → Nat → Prop := fun a b => a ≤ b
```

`def Le` — 새 이름 `Le` 의 정의. Le 는 영어 "less than or equal" 의 머리글자이다.

`: Nat → Nat → Prop` — 타입. 새 기호 두 개가 들어 있다.

`→` — 화살표. 영어 단어 "to", 한국어 "에서 ~로". 함수 타입을 만드는 기호. 키보드 `\to` 또는 `\->`. `A → B` 의 의미는 "A 에서 B 로 가는 함수의 타입", 곧 A 를 입력으로 받아 B 를 출력하는 함수들의 모임이다.

`Nat → Nat → Prop` 의 의미를 본다. Lean 4 의 `→` 는 오른쪽 결합 (right-associative) 이다. 곧 `Nat → Nat → Prop` 가 내부에서 `Nat → (Nat → Prop)` 로 해석된다.

뜻은 "자연수 하나를 받아, (자연수에서 명제로 가는 함수) 를 돌려주는 함수". 곧 함수가 두 자연수를 차례로 받아 명제를 돌려준다.

이런 방식이 Curry 화 (currying) 이다. 영어 "currying", 한국어 "커리화". 하스켈 커리 (Haskell Curry) 라는 수학자의 이름에서 왔다. 다중 인수 함수를 단일 인수 함수의 연속으로 표현하는 기법으로 Lean 4, Haskell, OCaml 등 함수형 언어의 표준이다.

`Prop` — 새 타입. 영어 "proposition" 의 줄임. 한국어 "명제". 진술은 "참 또는 거짓인 주장의 타입".

`Nat → Nat → Prop` 전체는 "두 자연수를 받아 명제를 돌려주는 함수의 타입", 정확히 "두 자연수 사이의 관계" 를 표현하는 타입이다.

비유 — `Le a b` 가 "a 와 b 가 부등식 a ≤ b 라는 관계에 있다" 라는 명제이다. 명제이므로 참 또는 거짓이다.

### 연결고리 — 멤버쉽 술어 (membership predicate)

집합 S 에 대해 $\chi_S(x) = (x \in S)$ 가 특성 함수이다. 이 특성 함수가 "x 가 집합 안에 있는가" 를 명제로 답한다. 정확히 두 표현의 다리이다.

Lean 4 가 함수 표현을 선택한 이유 — 함수가 계산에 더 자연스럽기 때문이다. 부분 적용 (partial application), 합성, 람다 등 도구가 풍부하다. 집합 자체는 계산 도구가 더 적다.

`:= fun a b => a ≤ b` — 함수 본체.

`fun` — 람다 함수 (lambda function) 의 키워드. 영어 단어 그대로. 한국어 "익명 함수" 또는 그냥 "fun". 진술은 "이름 없는 함수를 만드는 도구".

`fun a b =>` — "두 인수 a, b 를 받아". 이 부분이 함수의 입력 자리이다.

`=>` — 화살표. "그 결과는". 키보드 `=>` 그대로 두 글자, 또는 `\Rightarrow` 입력.

`a ≤ b` — 결과. "a 가 b 이하" 라는 명제.

`≤` — 부등식 기호. 작거나 같음. 키보드 `\le` 또는 `\leq`. 수학에서 보는 그 기호이다.

전체 의미 — "두 자연수 a, b 를 받아 a ≤ b 라는 명제를 돌려주는 함수가 Le 이다." 곧 `Le 1 3` 을 평가하면 결과는 `1 ≤ 3` 이라는 명제이다. 그 명제가 참인지 거짓인지는 또 다른 문제 (당연히 참) 이다.

학생들이 자주 묻는 의문 — "수학에서는 그냥 ≤ 가 있는데 왜 굳이 새로 Le 를 정의하나요?" 교육용이다. Mathlib 에 이미 `≤` 가 정의되어 있으므로 실용적으로는 새 Le 가 필요 없다. 그러나 "관계가 어떻게 함수로 표현되는지" 를 학생에게 명시적으로 보이기 위해 새 정의를 만들었다. 실전 코드에서는 Mathlib 의 `≤` 를 그대로 사용한다.

또 한 가지 — `def Le (a b : Nat) : Prop := a ≤ b` 처럼도 쓸 수 있다. 두 표기가 완전히 동등하다. 우리 형태는 람다로 본체를 정의하는 형태이며 함수의 본질을 보여 줘서 학습에 좋다.

다음 블록에서 이 Le 를 실제로 사용한다.

## 블록 7 — `Le 1 3` 의 증명

```lean
-- a R b 는 Lean 에서 R a b 로 쓴다.
example : Le 1 3 := by
  show 1 ≤ 3
  omega
```

Le 를 실제로 사용한다. "1 이 3 이하" 라는 사실을 Lean 4 로 증명한다.

`Le 1 3` — 함수 호출. 함수 `Le` 에 두 인수 `1` 과 `3` 을 차례로 적용한다. 결과는 명제 `1 ≤ 3`.

함수 호출 표기에 주목한다. Lean 4 에서 함수 적용은 공백으로 표현한다. `Le(1, 3)` 같이 괄호를 쓰지 않는다. 그냥 `Le 1 3` — 함수 이름 다음 공백, 첫 인수, 공백, 둘째 인수이다. 함수형 프로그래밍의 표준 표기이며 Python, C 와는 다른 스타일이다. 처음에 낯설지만 곧 익숙해진다.

수학 표기와의 대응 — 수학에서 $a\,R\,b$ 또는 $(a, b) \in R$. Lean 4 에서 `R a b`. 공백 하나의 차이이다.

`example : Le 1 3 := by` — "Le 1 3 이라는 명제를 증명한다" 라는 example. by 로 전술 모드.

`show 1 ≤ 3` — 새 전술.

`show` — 영어 단어 그대로 "보이다, 명시하다". 한국어 "명시". 진술은 "현재 목표를 같은 의미의 다른 형태로 다시 적는다".

지금 목표가 `Le 1 3`. Le 의 정의를 펼치면 `Le 1 3` 가 `(fun a b => a ≤ b) 1 3` 이 되고, 평가하면 `1 ≤ 3`. 곧 `Le 1 3` 과 `1 ≤ 3` 이 정의상 동등 (definitionally equal) 하다.

`show 1 ≤ 3` 가 하는 일 — "지금 보이려는 게 사실 1 ≤ 3 이다" 라고 명시적으로 알린다. Lean 4 가 두 형태의 동등성을 확인하고 목표를 새 형태로 변환한다.

InfoView 변화 — 전에는 목표 `Le 1 3`, 후에는 목표 `1 ≤ 3`. 시각적으로 더 명확하다.

학생들이 자주 묻는 의문 — "그럼 show 는 꼭 필요한가요?" 대부분 안 적어도 된다. 다음 전술 `omega` 가 자동으로 정의를 펼친다. 그러나 명시성을 위해 적었다. 학습 단계에서는 "지금 무엇을 증명하고 있는지" 를 매번 명시하는 게 좋다.

`omega` — 블록 5 에서 본 그 전술. 선형 정수 산술의 결정 알고리즘. 목표 `1 ≤ 3` 가 자명하다. omega 가 즉시 닫는다.

이 짧은 example 의 핵심 — "관계가 함수처럼 호출되고, 그 함수의 결과 명제가 증명 가능하다". 종이에 적은 "1 R 3" 이 Lean 4 의 "Le 1 3" 으로 그대로 옮겨졌다. 수학과 코드의 1:1 대응은 한 줄로 `a R b` 가 `R a b` 이다.

## 블록 8 — 항등관계 `IdRel`

```lean
-- 항등관계
def IdRel (A : Type) :
    A → A → Prop :=
  fun x y => x = y

-- 모든 x 에 대해 x 는 자기 자신과 항등관계에 있다
example (x : Nat) :
    IdRel Nat x x := by
  show x = x
  rfl
```

이번엔 항등관계 (identity relation) 이다. 모든 원소가 자기 자신하고만 관계 맺는 가장 단순한 관계이다.

`def IdRel (A : Type) : A → A → Prop := fun x y => x = y` — 정의.

`IdRel` — Identity Relation 의 줄임. 항등관계이다.

`(A : Type)` — 새 인수. 명시 인수 (explicit argument) 이다.

`A` — 타입의 이름. 대문자로 적는 게 관습이다. 우리가 어떤 타입 위에서 항등관계를 정의할지 그 자리에 두는 표시이다.

`: Type` — A 의 타입이 `Type`.

`Type` — 새 키워드. "타입의 타입". Lean 4 에서는 모든 것이 타입을 가지는데, 자연수의 타입은 `Nat`, 정수의 타입은 `Int`, 명제의 타입은 `Prop` 이다. 그러면 `Nat` 자체의 타입은? `Type` 이다. 곧 "타입들이 모인 우주".

이게 우주 계층 (universe hierarchy) 의 개념이다. 영어 "type universe", 한국어 "타입 우주". 진술은 "타입의 타입을 표현하는 메타 단계".

학생들이 자주 묻는 의문 — "그러면 Type 의 타입은 또 있나요?" 매우 좋은 질문이다. `Type 1` 이 있고 그 위는 `Type 2`. 무한히 올라간다. `Type 0` 이 보통 우리가 쓰는 `Type` 이다. 이걸 가지고 러셀의 역설 같은 모순을 피하는 게 우주 계층의 역할이다. 깊은 주제이지만 실용에서는 그냥 `Type` 만 알면 충분하다.

`(A : Type)` 의 의미 — "어떤 타입 A 를 명시 인수로 받음". 호출할 때 직접 적어 줘야 한다.

`: A → A → Prop` — 반환 타입. "A 위의 관계 (A 와 A 사이의 관계)".

`:= fun x y => x = y` — 함수 본체. 두 인수 x, y 에 대해 명제 `x = y` 를 돌려준다.

수학의 항등관계 정의 $I_A = \{(x, x) \mid x \in A\}$. 곧 "x 와 y 가 항등관계에 있다 ↔ x 와 y 가 같음". Lean 4 표현 `fun x y => x = y` 와 정확히 같다.

`=` — 등호. 두 객체가 같다는 명제. 결과가 명제 (`Prop` 타입) 이다.

두 번째 example.

`example (x : Nat) : IdRel Nat x x := by` —

`(x : Nat)` — 임의의 자연수 x.

`IdRel Nat x x` — 함수 호출. `IdRel` 에 세 인수 `Nat`, `x`, `x` 차례로 적용한다.

인수 세 개에 주목한다. 첫 인수 `Nat` 가 우리가 항등관계를 정의할 타입. 둘째와 셋째 `x, x` 가 관계의 두 원소이다. 평가하면 `IdRel Nat` 가 자연수의 항등관계 함수이고, 그 함수에 `x, x` 를 적용하면 결과는 명제 `x = x` 이다.

"왜 `IdRel x x` 가 아니라 `IdRel Nat x x` 인가?" `IdRel` 정의에서 `(A : Type)` 가 명시 인수였기 때문이다. 명시 인수는 호출 시 반드시 적어야 한다. 그래서 첫 자리에 타입 `Nat` 를 적는다. 대안으로 만약 `{A : Type}` (중괄호) 라고 정의했다면 암묵 인수가 되어 호출 시 생략 가능하다.

`:= by` — 전술 모드.

`show x = x` — 목표를 명시한다. `IdRel Nat x x` 가 정의상 `x = x` 와 같다. show 가 시각적으로 명시한다.

`rfl` — 익숙한 그 전술. `x = x` 가 자명하다. rfl 이 닫는다.

수학적 의미 — "모든 자연수 x 에 대해 x 가 자기 자신과 항등관계에 있다." 이게 항등관계의 가장 기본적인 성질이다. 모든 원소가 자기와 관계를 맺는다.

항등관계는 모든 관계 성질 (반사·대칭·추이) 을 자명히 만족한다. 반사성 `x = x`, 대칭성 `x = y → y = x`, 추이성 `x = y, y = z → x = z`. 모두 등호의 기본 성질이다. 그래서 항등관계가 동치관계의 가장 단순한 예이며 relation 의 5.4 절에서 다루는 그 관계이다.

"왜 `Nat` 만 쓰나요? 다른 타입에서도 IdRel 이 작동하나요?" `IdRel Int`, `IdRel String`, 또는 우리가 정의한 어떤 타입에서도 작동한다. `(A : Type)` 가 다형성 (polymorphism) 이다. 모든 타입에 통하는 일반적 정의이다.

## 블록 9 — 관계 합성 `Comp` 와 `RPow2`

```lean
-- 합성: a 에서 b 로 R, b 에서 c 로 S 면, a 에서 c 로 S∘R
def Comp {A : Type} (R S : A → A → Prop) :
    A → A → Prop :=
  fun a c => ∃ b, R a b ∧ S b c

-- R 의 제곱: R 을 두 번 합성
def RPow2 {A : Type} (R : A → A → Prop) :
    A → A → Prop :=
  Comp R R
```

이번엔 합성 (composition) 이다. relation 의 5.5 절에서 다룬 그 연산이다.

`def Comp {A : Type} (R S : A → A → Prop) : A → A → Prop := fun a c => ∃ b, R a b ∧ S b c`

먼저 새 표기 `{A : Type}`. `{` 와 `}` 가 중괄호이며 명시 인수의 `(` 와 다른 표기이다.

`{A : Type}` — 암묵 인수 (implicit argument). 영어 "implicit argument", 한국어 "암묵 인수". 진술은 "호출 시 적지 않아도 Lean 4 가 문맥에서 자동 추론한다".

대조로 명시 인수 `(A : Type)` 는 호출 시 반드시 적어야 하고, 암묵 인수 `{A : Type}` 는 생략한다.

왜 여기서 암묵을 쓰는가 — `Comp R S` 라는 호출에서 R 과 S 의 타입이 `A → A → Prop` 이다. Lean 4 가 R, S 의 타입을 보고 A 를 자동 추론 가능하다. 매번 `Comp Nat R S` 처럼 타입을 명시할 필요가 없어 편의를 위한 것이다.

학생들이 자주 묻는 의문 — "그러면 IdRel 도 암묵으로 하면 안 되나요?" 좋은 시도이다. IdRel 호출에서 `IdRel x x` 라고 적으면 x 의 타입에서 A 를 추론 가능하므로 가능하다. 다만 블록 8 에서는 학습용으로 명시했다. 실전에서는 암묵이 더 자연스럽다.

`(R S : A → A → Prop)` — 두 명시 인수. 두 관계 R, S 이다. 한 괄호 안에 R 과 S 가 같이 있는 게 줄임 표기이며 `(R : A → A → Prop) (S : A → A → Prop)` 와 동등하지만 짧다.

`: A → A → Prop` — 반환 타입. 합성도 관계이다.

`:= fun a c => ∃ b, R a b ∧ S b c` — 함수 본체. 가장 중요한 부분이다.

`fun a c =>` — 두 인수 a, c 를 받는다. 합성 관계의 두 원소이다.

`∃ b,` — 새 기호. `∃` 는 존재 양화사 (existential quantifier). 영어 "there exists", 한국어 "존재한다". 키보드 `\exists` 또는 `\ex`. 진술은 "어떤 b 가 존재해서 그 조건을 만족". `∃ b, P` 의 의미는 "P 조건을 만족하는 b 가 적어도 하나 존재한다". 수학에서 보는 그 기호이며 $\exists b$ 와 같다.

`R a b ∧ S b c` — 조건. AND 두 명제이다. `R a b` 는 a 와 b 가 관계 R 에 있음, `S b c` 는 b 와 c 가 관계 S 에 있음, `∧` 는 AND 이다.

전체는 "어떤 b 가 존재해서 `R a b` 와 `S b c` 가 둘 다 성립한다."

이게 합성의 정의이다. relation 5.5 절에서 $S \circ R = \{(a, c) \mid \exists b : (a, b) \in R \wedge (b, c) \in S\}$ 와 정확히 같은 정의이다.

표기 순서에 주의한다. 수학에서 `S ∘ R` 의 의미는 "R 먼저, S 다음" — 오른쪽이 먼저 적용된다. 함수 합성의 관례이다. Lean 4 의 `Comp R S` 는 함수 인수 순서 그대로 "R 이 첫 인수, S 가 둘째" 이다.

"R 먼저, S 다음" 의 의미가 두 표기에서 같은지 확인한다. `Comp R S a c` 의 정의는 `∃ b, R a b ∧ S b c`. 곧 a 에서 R 로 b 까지 가고, b 에서 S 로 c 로 간다. R 먼저, S 다음. 수학의 $S \circ R$ 와 같은 의미이며 표기만 다르다.

학생들이 자주 묻는 의문 — "왜 수학 표기랑 Lean 표기가 순서가 반대처럼 보이나요?" 수학 표기 $S \circ R$ 는 함수 적용 관례에 따른 것으로 $f(g(x)) = (f \circ g)(x)$ 처럼 왼쪽이 나중이다. Lean 의 `Comp R S` 는 함수 인수 순서에 따른 것으로 왼쪽 인수가 먼저이다. 둘 다 같은 합성을 다른 관점에서 표기한 것이다.

`def RPow2 {A : Type} (R : A → A → Prop) : A → A → Prop := Comp R R`

`RPow2` — R 의 2 거듭제곱 (R Power 2). `Comp R R` 는 R 을 자기 자신과 합성한 것, 곧 길이 2 경로의 관계이며 relation 5.3 절의 $R^2$ 이다.

짧은 정의지만 의미가 깊다. R 의 거듭제곱이 Lean 4 에서 합성의 반복으로 표현된다. 수학에서 $R^2 = R \circ R$ 가 코드의 `Comp R R` 이다.

학생들이 자주 묻는 의문 — "그러면 $R^3, R^4$ 도 가능한가요?" 가능하다. 재귀적으로 정의 가능하다.

```
def RPow {A : Type} (R : A → A → Prop) : Nat → A → A → Prop
  | 0 => fun a b => a = b
  | n+1 => Comp R (RPow R n)
```

곧 $R^0$ 은 항등관계, $R^{n+1}$ 은 $R \circ R^n$. 모든 자연수 n 에 대해 자동이다. 이런 재귀 정의가 Lean 4 의 유도형 (inductive type) 시스템의 강점이다. 자세한 것은 따로 강의한다.

## 블록 10 — `Comp R R` 의 구성 예

```lean
example {A : Type}
    (R : A → A → Prop)
    (a b c : A)
    (hab : R a b)
    (hbc : R b c) :
    Comp R R a c := by
  -- 목표: ∃ m, R a m ∧ R m c
  -- 중간 정점으로 b 를 제시
  exact ⟨b, hab, hbc⟩
```

합성 관계의 멤버쉽을 직접 증명한다. "두 단계의 화살표가 있으면 합성 관계의 한 쌍을 만들 수 있다" 라는 사실이다.

`example {A : Type}` — 암묵 인수로 A. 호출 시 자동 추론된다.

`(R : A → A → Prop)` — 관계 R 을 명시 인수로.

`(a b c : A)` — 세 원소.

`(hab : R a b)` — 가설 hab. 이름이 의미를 담는다. h 더하기 a 더하기 b 로 "a 와 b 사이의 가설".

`(hbc : R b c)` — 가설 hbc. b 와 c 사이의 가설이다.

이런 이름 짓기가 가독성이 좋다. 다른 사람이 코드를 읽을 때 `hab` 가 무엇인지 즉시 짐작 가능하다.

`: Comp R R a c` — 결론. "a 와 c 가 R 의 자기 합성 관계에 있다", 곧 길이 2 경로의 한 쌍이다.

`:= by` — 전술 모드. 그러나 사실은 한 줄로 끝난다.

`exact ⟨b, hab, hbc⟩` — 증명의 전부.

`exact` — 영어 단어 그대로 "정확히". 한국어 "정확". 진술은 "정확히 이 항이 목표의 증명임을 제공".

`⟨b, hab, hbc⟩` — 꺽쇠 표기. 블록 5 에서 본 그 꺽쇠이다. 그러나 이번에는 분해가 아니라 묶음이다.

분석한다. 목표 `Comp R R a c` 를 정의대로 펼치면 `∃ m, R a m ∧ R m c`. 증명을 위해 필요한 것은 (1) 어떤 m 인지 증인 (witness) 제시, (2) `R a m` 의 증명, (3) `R m c` 의 증명이다.

꺽쇠 `⟨b, hab, hbc⟩` 가 세 부분이다. `b` 는 증인 — m 자리에 b 를 제시하며 "중간 정점이 b 이다" 라는 선언. `hab` 는 `R a b` 의 증명 — 가설 hab 가 정확히 이 형태. `hbc` 는 `R b c` 의 증명 — 가설 hbc.

그러면 우리가 증명한 것은 "중간 정점 m = b 가 존재하고, 그 b 에 대해 R a b 와 R b c 가 모두 성립" 이며 따라서 "Comp R R a c 가 성립" 한다.

이게 존재 증명의 표준 패턴 — 증인을 직접 제시하는 것이다. 구성적 증명 (constructive proof) 이라 부른다. 영어 "constructive", 한국어 "구성적". 진술은 "존재 명제를 증명할 때 그 객체를 실제로 만들어 제시한다".

InfoView 변화 — 전에는 목표 `Comp R R a c`, 후에는 `No goals`. 한 줄로 끝난다.

학생들이 자주 묻는 의문 — "꺽쇠 안에 세 가지가 있는데, 정확히 어떻게 작동하나요?" 자동 평탄화 (automatic flattening) 때문이다. `⟨b, hab, hbc⟩` 가 사실 `⟨b, ⟨hab, hbc⟩⟩` 의 줄임이다. 바깥 꺽쇠 `⟨b, ⟨hab, hbc⟩⟩` 는 존재 명제의 증명으로 두 부분 (증인 더하기 본체), 안쪽 꺽쇠 `⟨hab, hbc⟩` 는 합접의 증명으로 두 부분이다. 곧 외층이 ∃ 의 증명, 내층이 ∧ 의 증명이다. 두 꺽쇠가 중첩되고 Lean 4 가 평탄화해서 한 꺽쇠로 적을 수 있게 해 준다.

가설 `hab : R a b` 와 `hbc : R b c` 가 이미 `b` 라는 정점에 대해 주어진다. 증인이 가설에서 직접 제공된다. 일반 증명에서는 증인을 직접 구성해야 하는 어려운 작업이지만 우리 예제는 가설이 친절해서 쉽다.

"왜 `exact` 인가? 다른 전술도 가능?" `refine ⟨b, hab, hbc⟩` 도 가능하다. 차이는 `exact` 가 완전 일치를 요구하고 `refine` 는 부분적 미완성을 허용한다는 것이다. 우리 경우는 완전하므로 exact 이다. 또는 꺽쇠 없이 명시적 함수 호출 `Exists.intro b (And.intro hab hbc)` 도 정확히 같은 의미지만 길다. 꺽쇠가 가독성과 간결성이 좋다.

수학적 의미 — "$a \to b$ 화살표와 $b \to c$ 화살표가 있으면, $a \to c$ 의 길이 2 경로가 존재" 라는 자연스러운 사실이다. 종이에 한 줄로 적을 그 사실이 Lean 4 의 한 줄 코드이다.

## 블록 11 — 합성의 결합법칙

```lean
example {A : Type} (R S T : A → A → Prop) (a d : A) :
    Comp (Comp R S) T a d ↔ Comp R (Comp S T) a d := by
  constructor
  · rintro ⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩
    -- 왼쪽 묶음을 풀면 b, c 라는 두 중간 정점이 나온다
    exact ⟨b, hRab, c, hSbc, hTcd⟩
  · rintro ⟨b, hRab, c, hSbc, hTcd⟩
    -- 오른쪽 묶음을 풀어 같은 b, c 로 왼쪽을 구성
    exact ⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩
```

가장 큰 정리이다. 합성의 결합법칙 (associativity) $(T \circ S) \circ R = T \circ (S \circ R)$.

`example {A : Type} (R S T : A → A → Prop) (a d : A)` — 세 관계 R, S, T 와 두 정점 a, d.

`: Comp (Comp R S) T a d ↔ Comp R (Comp S T) a d` — 결론.

`Comp (Comp R S) T a d` 는 `R ∘ S` 를 먼저 하고 `T` 를 다음에, 곧 (R 과 S 합성) 과 T 의 합성이다. `Comp R (Comp S T) a d` 는 R 을 먼저 하고 `S ∘ T` 를 다음에, 곧 R 과 (S 와 T 합성) 의 합성이다.

`↔` — 둘이 동치. 양방향이다. 수학으로 "어떤 순서로 묶어 합성하든 결과 동일" — 결합법칙이다.

`:= by constructor` — `constructor` 는 블록 5 에서 본 그 전술. 결론이 `↔` 형태일 때 두 부 목표로 분해하여 양방향을 따로 다룬다.

InfoView 변화 — 전에는 목표 `Comp (Comp R S) T a d ↔ Comp R (Comp S T) a d`, 후에는 두 부 목표 (1) 왼쪽에서 오른쪽 방향, (2) 오른쪽에서 왼쪽 방향이다.

첫 부 목표.

`· rintro ⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩` —

`·` — 부 목표 시작.

`rintro` — 새 전술. recursive intro 의 줄임이다.

`intro` — 영어 단어 그대로 "도입". 한국어 "도입". 진술은 "가정을 받아 자유 변수로 둠".

`rintro` 는 `intro` 의 강화판이다. 가정을 받으면서 동시에 패턴 매칭으로 분해한다.

`⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩` — 중첩 꺽쇠. 가정의 구조를 그대로 풀어 적는다.

분석한다. 첫 부 목표의 가정 `Comp (Comp R S) T a d` 의 정의를 펼치면 `∃ c, (Comp R S) a c ∧ T c d`. 여기 `Comp R S` 를 또 펼치면 `∃ c, (∃ b, R a b ∧ S b c) ∧ T c d`. 곧 중간 정점 c 존재, 그 c 에 대해 더 중간 정점 b 존재, `R a b`, `S b c`, `T c d` 모두 성립이다.

꺽쇠 `⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩` 가 이 구조를 그대로 분해한다. `c` 는 외층 ∃ 의 증인. `⟨b, hRab, hSbc⟩` 는 외층 ∧ 의 왼쪽 부분, 내층 ∃ ∧ 이다 — `b` 는 내층 ∃ 의 증인, `hRab` 는 `R a b` 의 증명, `hSbc` 는 `S b c` 의 증명. `hTcd` 는 외층 ∧ 의 오른쪽 부분, `T c d` 의 증명이다.

InfoView 변화 — 전에는 가정 `Comp (Comp R S) T a d`, 후에는 `c, b : A`, `hRab : R a b`, `hSbc : S b c`, `hTcd : T c d` 모두 자유 변수와 가설로 도입된다.

`exact ⟨b, hRab, c, hSbc, hTcd⟩` — 결론을 구성한다.

목표 `Comp R (Comp S T) a d` 의 정의를 펼치면 `∃ b, R a b ∧ (∃ c, S b c ∧ T c d)`. 꺽쇠 `⟨b, hRab, c, hSbc, hTcd⟩` 가 이 구조를 그대로 구성한다. `b` 는 외층 ∃ 의 증인, `hRab` 는 외층 ∧ 의 왼쪽 R a b 의 증명, `c` 는 내층 ∃ 의 증인, `hSbc` 는 내층 ∧ 의 왼쪽 S b c 의 증명, `hTcd` 는 내층 ∧ 의 오른쪽 T c d 의 증명이다.

곧 왼쪽 표현에서 얻은 정보를 그대로 오른쪽 형식으로 재배열한다. 내용은 같고 묶는 방식만 다르다.

`· rintro ⟨b, hRab, c, hSbc, hTcd⟩` 와 `exact ⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩` 는 둘째 부 목표이다. 같은 일을 반대 방향으로 한다. 오른쪽 표현을 분해하고 왼쪽 형식으로 재구성한다. 거의 복사·붙여넣기 수준의 대칭성이다.

결합법칙의 의미 — "같은 중간 정점들을 다르게 묶은 것뿐" 이다. 왼쪽도 오른쪽도 결국 같은 b, c 두 중간 정점을 사용하며 묶는 방식만 다르다.

학생들이 자주 묻는 의문 — "함수 합성의 결합법칙은 자명한 줄 알았는데, Lean 증명이 이렇게 긴 이유는?" 수학에서 자명한 사실도 Lean 4 에서는 정확한 단계가 필요하다. 왼쪽 형식과 오른쪽 형식이 글자 그대로 같지 않으므로 꺽쇠 분해와 재조립이 명시된다. 형식 증명의 본성이다. 다만 Mathlib 에는 결합법칙이 이미 증명되어 있어 실전에서는 한 줄 호출이다. 우리는 원리 이해를 위해 직접 증명한다. 교육용이다.

또 의문 — "`rintro` 와 `intro` 더하기 `obtain` 의 차이는?" 기능은 같지만 표기가 압축적이다. `rintro ⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩` 가 `intro h; obtain ⟨c, hc⟩ := h; ...` 같은 여러 줄을 한 줄로 줄인다. 길이는 4분의 1 이다.

## 블록 12 — 다섯 가지 관계 성질의 정의

```lean
variable {A : Type}

def Refl  (R : A → A → Prop) : Prop := ∀ a, R a a
def Symm  (R : A → A → Prop) : Prop := ∀ a b, R a b → R b a
def Trans1 (R : A → A → Prop) : Prop :=
  ∀ a b c, R a b → R b c → R a c
def Antisymm (R : A → A → Prop) : Prop :=
  ∀ a b, R a b → R b a → a = b

-- 동치관계: 세 성질을 ∧ 로 묶는다
def Equiv1 (R : A → A → Prop) : Prop :=
  Refl R ∧ Symm R ∧ Trans1 R
```

이번이 relation 5.4 절의 핵심이다. 다섯 가지 성질을 Lean 4 로 옮긴다.

먼저 첫 줄 `variable {A : Type}`.

`variable` — 영어 단어 그대로 "변수". 한국어 "변수". 진술은 "이 파일에서 다음 정의들에 자동으로 추가될 인수를 선언".

`{A : Type}` — 암묵 인수 A 를 선언한다. `variable {A : Type}` 의 의미는 "이 줄 이후 모든 def 와 example 에서 `{A : Type}` 가 자동으로 추가된다". 곧 매번 `{A : Type}` 를 적지 않아도 된다.

### variable 이 정확히 어디까지 적용되는가

같은 namespace 또는 section 안의 후속 정의들에 적용된다. 우리 파일에서는 그 뒤의 모든 def 와 example 이다. 명시적으로 끝내려면 `section` 과 `end` 같은 블록을 따로 두는데 우리 코드는 단순히 파일 전체에 적용한다.

이제 다섯 정의를 차례로 본다.

### Refl — 반사성

`def Refl (R : A → A → Prop) : Prop := ∀ a, R a a`

`Refl` — Reflexive (반사적) 의 줄임.

`(R : A → A → Prop)` — 관계 R 을 명시 인수로.

`: Prop` — 반환 타입. 명제. 곧 "Refl R" 자체가 명제이며 "R 이 반사관계이다" 라는 주장이다.

`:= ∀ a, R a a` — 본체.

`∀` — 새 기호. 전체 양화사 (universal quantifier). 영어 "for all", 한국어 "모든". 키보드 `\forall` 또는 `\all`. 진술은 "모든 a 에 대해 그 다음 조건이 성립". 수학의 $\forall$ 와 같다.

`∀ a, R a a` — "모든 a 에 대해 R a a 가 성립". 곧 모든 원소가 자기 자신과 R 관계를 맺는다.

수학적 정의 — R 이 반사관계인 것은 $\forall a, (a, a) \in R$ 과 동치. Lean 4 표현과 1:1 대응한다.

### Symm — 대칭성

`def Symm (R : A → A → Prop) : Prop := ∀ a b, R a b → R b a`

`Symm` — Symmetric (대칭적).

`∀ a b, R a b → R b a` — "모든 a, b 에 대해 R a b 이면 R b a".

`∀ a b,` — 변수 두 개의 양화. `∀ a, ∀ b,` 의 줄임이다.

`→` — 함수 화살표인데 여기서는 함의 (implication) 의 의미이다. "~이면 ~".

함수 타입의 `→` 와 함의의 `→` 가 같은 기호이다. 우연이 아니라 두 개념이 본질적으로 같다. "P 이면 Q" 는 "P 의 증명을 Q 의 증명으로 변환하는 함수" 이다. 깊은 논리학 사실이다.

수학적 정의 — R 이 대칭관계인 것은 $\forall a, b, (a, b) \in R \to (b, a) \in R$ 과 동치. 1:1 대응한다.

### Trans1 — 추이성

`def Trans1 (R : A → A → Prop) : Prop := ∀ a b c, R a b → R b c → R a c`

`Trans1` — Transitive (추이적) 의 일종. 1 이 붙은 이유는 Mathlib 의 `Transitive` 와 이름이 충돌하지 않게 하기 위해서이다. 우리 정의는 학습용 사본이다.

`∀ a b c, R a b → R b c → R a c` — 세 변수와 두 함의.

`R a b → R b c → R a c` — "R a b 이면 (R b c 이면 R a c)" 의 의미. 함의가 연속이다.

함의 화살표가 두 번 연속이다. Lean 4 의 `→` 는 오른쪽 결합이므로 `A → B → C` 가 `A → (B → C)`, 곧 "A 이면 (B 이면 C)" 이다. 곧 "R a b 와 R b c 가 둘 다 주어지면 R a c" — 추이성이다.

학생들이 자주 묻는 의문 — "왜 함의 두 개고 합접 (∧) 한 개가 아닌가요?" 둘 다 가능하다. `R a b ∧ R b c → R a c` 와 `R a b → R b c → R a c` 가 논리적으로 동등하다. 다만 후자가 부분 적용에 편리하다. "R a b 만 받아 (R b c → R a c) 라는 함수를 돌려줌" — 두 단계 적용이 가능하다.

### Antisymm — 반대칭성

`def Antisymm (R : A → A → Prop) : Prop := ∀ a b, R a b → R b a → a = b`

`Antisymm` — Antisymmetric (반대칭적).

`∀ a b, R a b → R b a → a = b` — "모든 a, b 에 대해, R a b 이고 R b a 이면 a = b". 곧 양방향 관계가 있으면 같은 원소여야 한다. 7 장의 부분순서관계의 핵심 성질이다.

`a = b` — 결론이 등식. Prop 타입이다.

### Equiv1 — 동치관계

`def Equiv1 (R : A → A → Prop) : Prop := Refl R ∧ Symm R ∧ Trans1 R`

`Equiv1` — Equivalence (동치).

`Refl R ∧ Symm R ∧ Trans1 R` — 세 성질의 합접. 동치관계의 정의이다.

합접이 두 번 연속이다. `A ∧ B ∧ C` 가 `A ∧ (B ∧ C)` 로 오른쪽 결합한다. 블록 16 의 증명에서 두 번 분해해야 하는 이유이다.

수학적 정의 — R 이 동치관계인 것은 R 이 반사 그리고 대칭 그리고 추이인 것과 동치. relation 5.4 절의 봉우리이다.

학생들이 자주 묻는 의문 — "다섯 가지 성질이라 했는데 정의는 네 개 더하기 동치관계 = 다섯 인가요? 비반사, 비대칭은?" 우리 코드는 다섯 중 네 가지만 정의한다. 비반사, 비대칭은 부정 (¬) 을 써서 정의 가능하다. `def Irrefl (R : A → A → Prop) : Prop := ∀ a, ¬ R a a` 가 비반사, `def Asymm (R : A → A → Prop) : Prop := ∀ a b, R a b → ¬ R b a` 가 비대칭이다. `¬` 는 부정으로 블록 18 에서 자세히 다룬다.

또 의문 — "Mathlib 에 이미 같은 정의가 있나요?" 그렇다. `Reflexive`, `Symmetric`, `Transitive`, `Equivalence` 가 Mathlib 표준 이름이다. 우리 정의는 학습용 변종이며 실전에서는 Mathlib 을 사용한다.

## 블록 13 — `Le` 가 반사관계임을 증명

```lean
def Le1 : Nat → Nat → Prop :=
  fun a b => a ≤ b

-- Le 는 반사관계
example : Refl Le := by
  -- 목표: ∀ a, Le a a
  intro a
  show a ≤ a
  omega
```

첫 형식 증명이다. `Le` 가 반사관계임을 증명한다.

먼저 `def Le1` 은 블록 6 의 `Le` 와 같은 정의이지만 이름이 `Le1` 이다. 이유는 Mathlib 의 다른 정의와의 충돌 회피, 그리고 후속 `unfold` 명령에서의 안전한 펼침이다. 학습용 의도된 중복이다.

`example : Refl Le := by` — "Le 가 반사관계임을 증명한다."

결론 `Refl Le` 가 명제이다. `Refl` 정의를 펼치면 `∀ a, Le a a`. 곧 모든 자연수 a 에 대해 `Le a a` 가 성립한다.

`:= by intro a` —

`intro` — 새 전술. 영어 "introduce", 한국어 "도입". 진술은 "전체 양화사 ∀ 또는 함의 → 를 푸는 전술".

`∀ a, P a` 형태의 목표에 `intro a` 를 적용하면 "임의의 a 를 잡고, 그 a 에 대해 P a 를 보이겠다" 로 변환된다. 수학에서 "임의의 a 를 잡는다" 와 정확히 같다.

InfoView 변화 — 전에는 목표 `∀ a, Le a a`, 후에는 자유 변수 `a : Nat` 와 목표 `Le a a`. 양화사가 사라지고 자유 변수가 등장한다.

`show a ≤ a` — 목표 명시. `Le a a` 의 정의를 펼치면 `(fun a b => a ≤ b) a a` 가 평가되어 `a ≤ a`. 곧 `Le a a` 가 정의상 `a ≤ a` 이다. show 가 두 형태의 동등성을 명시한다.

InfoView 변화 — 전에는 목표 `Le a a`, 후에는 목표 `a ≤ a`. 시각적으로 명확하다.

`omega` — 익숙한 그 전술. `a ≤ a` 가 모든 자연수에 자명하다. omega 가 즉시 닫는다.

수학과 Lean 4 의 1:1 대응.

| 수학 | Lean 4 |
|---|---|
| "임의의 a 를 잡고" | `intro a` |
| "Le 의 정의에 의해 a ≤ a" | `show a ≤ a` |
| "a ≤ a 자명" | `omega` |

세 줄로 끝난다. 형식 증명의 매끄러움이다.

"`show` 가 꼭 필요한가?" 생략 가능하다. omega 가 자동으로 정의를 펼친다. 우리 코드는 학습용 명시성을 위한 것이며 실전에서는 `intro a; omega` 두 줄이면 충분하다.

"왜 a 가 두 번 등장하는데 intro 가 한 번만?" `∀ a, R a a` 가 한 변수 a 에 대한 양화이다. R a a 안에서 a 가 두 번 나타나지만 한 변수의 두 번 사용이다. 그래서 intro a 한 번이면 충분하다.

"intro 의 자유 변수가 정확히 무엇인가?" `intro a` 후 a 가 임의의 자연수를 나타내는 자유 변수이다. "어떤 특정 a 도 아니고 모든 a 를 대표하는 a" 이다. 수학적으로 같은 의미이다.

## 블록 14 — `EqR` 가 대칭관계임을 증명

```lean
def EqR (A : Type) :
    A → A → Prop :=
  fun a b => a = b


example {A : Type} :
    Symm (EqR A) := by
  -- ∀ a b, a=b → b=a
  intro a b h
  show b = a
  exact h.symm
```

### `EqR` 정의

영어 "Equality Relation" 의 줄임이다. 등호 관계를 명시적 함수로 표현한다.

`def EqR (A : Type) : A → A → Prop := fun a b => a = b` — 타입 매개변수 A 를 명시 인수로 받고, 두 인수 a, b 를 받아 `a = b` 명제를 반환한다. 수학에서 등호 `=` 자체가 한 관계인데 그걸 함수로 명시적으로 표현한 것이다.

`example {A : Type} : Symm (EqR A) := by`

`{A : Type}` — 암묵 인수. (앞서 `variable {A : Type}` 가 있어 사실 생략 가능하지만 명시했다.)

`Symm (EqR A)` — "EqR 이 대칭관계이다" 라는 명제. `Symm` 정의를 펼치면 `∀ a b, R a b → R b a` 이며 R 자리에 EqR A 가 들어간다.

`intro a b h` — `intro` 가 세 가지를 동시에 받는다. `∀ a b, R a b → R b a` 의 구조는 (1) ∀ a, (2) ∀ b, (3) 함의의 가설 R a b 이다. `intro a b h` 가 세 단계를 한 줄에 — a, b, 그리고 함의 가설 h 를 차례로 받는다. 짧고 효율적이다. `intro` 가 한 번에 여러 개 받을 수 있는 게 Lean 4 의 편의이며 `intro a; intro b; intro h` 세 줄과 동등하다.

InfoView 변화 — 전에는 목표 `∀ a b, EqR A a b → EqR A b a`, 후에는 `a b : A`, `h : EqR A a b` (정의 펼침으로 `h : a = b`), 목표 `EqR A b a` (= `b = a`) 이다.

`show b = a` — 목표 명시.

`exact h.symm` — 새 전술 사용.

`h.symm` — 점 표기. `h` 의 점 다음 `symm` 메서드이다.

`symm` — Symmetric (대칭) 의 줄임. 등호 또는 동치관계의 대칭성을 적용하는 함수이다. `h : a = b` 가 있을 때 `h.symm` 은 `b = a` 의 증명이며 곧 `Eq.symm h` 의 단축 표기이다.

점 표기가 어떻게 작동하는가. `h` 의 타입이 `Eq` (등식) 이다. Lean 4 가 `Eq` 타입의 메서드 `symm` 을 찾아 자동 적용한다. `h.symm` 이 `Eq.symm h` 이다. 이런 점 표기가 Lean 4 의 매우 자주 쓰는 도구이며 가독성이 좋다.

`exact h.symm` — "정확히 h.symm 이 우리 목표 b = a 의 증명이다". exact 가 매칭을 확인하고 통과한다.

InfoView 변화 — 전에는 목표 `b = a`, 후에는 No goals.

수학과 Lean 4 의 대응.

| 수학 | Lean 4 |
|---|---|
| "임의의 a, b 잡고" | `intro a b` |
| "a = b 가정" | `intro h` |
| "등호 대칭으로 b = a" | `exact h.symm` |

수학 추론 3 단계가 코드 3 줄이다.

학생들이 자주 묻는 의문 — "`h.symm` 대신 다른 방법은?" 여러 가지 가능하다. `rw [h]` 는 h 의 좌우를 사용해 목표의 a 를 b 로 치환하여 목표 `b = a` 가 `b = b` 가 되고 자동 닫힌다. `exact Eq.symm h` 는 h.symm 의 풀이 형태이다. `symm` 은 그냥 전술로 목표가 등식이면 좌우를 교환하고 그 다음 `exact h` 한다. 세 방식 모두 같은 결과이며 점 표기가 가장 짧고 우아하다.

또 의문 — "h.symm 같은 점 표기가 어떻게 자동 작동하나요?" Lean 4 의 dot notation 자동 해석 덕분이다. `h.foo` 가 있으면 Lean 4 가 h 의 타입 T 를 보고 `T.foo h` 또는 적절한 변환을 시도한다. 우리 경우 `h : a = b` 의 타입이 `Eq a b` 이므로 `Eq.symm h` 를 호출한다. 매우 편리하다.

## 블록 15 — `Le1` 가 추이관계임을 증명

```lean
example : Trans1 Le1 := by
  -- ∀ a b c, Le1 a b → Le1 b c → Le1 a c
  intro a b c hab hbc
  -- hab : Le1 a b
  -- hbc : Le1 b c
  unfold Le1 at hab hbc
  -- 이제 hab : a ≤ b, hbc : b ≤ c
  show a ≤ c
  omega
```

추이성 증명이다. `Le1` 이 추이관계임을 증명한다.

`Trans1` 정의를 펼치면 `∀ a b c, R a b → R b c → R a c`. 곧 세 변수와 두 함의이다.

`intro a b c hab hbc` — 다섯 가지를 한 줄에 받는다. 세 변수 a, b, c 는 양화사 세 번, 두 가설 hab, hbc 는 함의 두 번이다. 가설 이름이 의미를 가진다. `hab` 는 "a 와 b 사이의 가설", `hbc` 는 "b 와 c 사이의 가설" 이다. 가독성이 좋다.

InfoView 변화 — 후에는 `a b c : Nat`, `hab : Le1 a b`, `hbc : Le1 b c`, 목표 `Le1 a c`.

`unfold Le1 at hab hbc` — 새 전술.

`unfold` — 영어 단어 "펴다, 펼치다". 한국어 "펼침". 진술은 "정의를 강제로 펼친다".

`unfold Le1` 은 Le1 의 정의 `Le1 := fun a b => a ≤ b` 를 펼친다. 펼친 결과는 `a ≤ b`.

`at hab hbc` — 두 가설에 동시 적용한다. 블록 5 에서 본 `at h` 의 확장이다.

InfoView 변화 — 전에는 `hab : Le1 a b`, `hbc : Le1 b c`, 후에는 `hab : a ≤ b`, `hbc : b ≤ c`. 정의가 펼쳐져 순수 부등식이 된다.

왜 `unfold` 가 필요한가. 목표는 `Le1 a c` 인데 우리가 `show a ≤ c` 로 명시할 예정이다. 그러나 가설 hab, hbc 도 omega 가 처리하려면 `a ≤ b`, `b ≤ c` 같은 순수 부등식이어야 한다. unfold 가 가설들을 그 형태로 바꾼다.

`show a ≤ c` — 목표를 부등식으로 명시.

`omega` — 두 부등식 가설과 목표를 종합한다. `a ≤ b` 이고 `b ≤ c` 이면 `a ≤ c` — 부등식의 추이성이다. omega 가 자동 도출한다.

학생들이 자주 묻는 의문 — "show 와 unfold 의 차이는?" 비슷하지만 위치가 다르다. `show` 는 목표만, `unfold` 는 목표·가설 모두 가능하다. 또 `show` 는 동등한 다른 형태를 명시하고 `unfold` 는 특정 정의를 펼친다. 둘 다 정의 등치를 활용한다.

또 의문 — "omega 가 두 부등식을 어떻게 결합하나요?" 선형 산술의 결정 알고리즘이다. 가설 `a ≤ b` 와 `b ≤ c` 를 행렬 형태로 정규화한 후 변수 b 를 소거한다. 결과 `a ≤ c` 가 우리 목표와 일치한다.

수학과 코드의 대응.

| 수학 | Lean 4 |
|---|---|
| "임의의 a, b, c 잡고" | `intro a b c` |
| "a ≤ b 와 b ≤ c 가정" | `intro hab hbc` |
| "Le1 의 정의 펼치면 부등식" | `unfold Le1 at hab hbc` |
| "보일 것은 a ≤ c" | `show a ≤ c` |
| "부등식 추이성으로 a ≤ c" | `omega` |

수학 5 단계가 코드 5 줄이다.

## 블록 16 — `EqR` 가 동치관계임을 증명

```lean
example {A : Type} : Equiv1 (EqR A) := by
  -- 목표: Refl (EqR A) ∧ Symm (EqR A) ∧ Trans1 (EqR A)
  constructor
  · intro a
    show a = a
    rfl
  · constructor
    · intro a b h
      show b = a
      exact h.symm
    · intro a b c hab hbc
      show a = c
      exact Eq.trans hab hbc
```

relation 5.4 절의 봉우리이다. 등호가 동치관계임을 증명한다. 세 성질을 한꺼번에 다룬다.

`Equiv1 (EqR A)` 의 정의를 펼치면 `Refl (EqR A) ∧ Symm (EqR A) ∧ Trans1 (EqR A)`. 세 성질의 합접이다. 합접이 두 번 연속이라 `A ∧ B ∧ C` 가 `A ∧ (B ∧ C)` 이므로 constructor 가 두 번 필요하다.

`constructor` — 첫 합접 분해.

InfoView 변화 — 전에는 목표 `Refl (EqR A) ∧ Symm (EqR A) ∧ Trans1 (EqR A)`, 후에는 두 부 목표 (1) `Refl (EqR A)`, (2) `Symm (EqR A) ∧ Trans1 (EqR A)`.

첫 부 목표 (반사성).

`· intro a; show a = a; rfl` — `intro a` 는 임의의 a 를 잡는다 (∀ a 분해). `show a = a` 는 목표를 등식으로 명시한다 (EqR A a a 가 정의상 a = a). `rfl` 은 자명하므로 닫는다.

두 번째 부 목표 `Symm (EqR A) ∧ Trans1 (EqR A)` 는 또 합접이다.

`· constructor` — 두 번째 합접 분해.

InfoView 변화 — 후에는 두 새 부 목표 (1) `Symm (EqR A)`, (2) `Trans1 (EqR A)`.

대칭성 부 목표는 블록 14 의 패턴 그대로이다. `· intro a b h; show b = a; exact h.symm`.

추이성 부 목표는 새로운 모습이다. `· intro a b c hab hbc` 는 세 변수와 두 가설. `show a = c` 는 목표 명시 (`EqR A a c` 가 `a = c`). `exact Eq.trans hab hbc` 는 새 도구이다.

`Eq.trans` — 등호의 추이성 정리. Mathlib 의 표준 정리이다. 시그너처는 `Eq.trans : a = b → b = c → a = c`. `Eq.trans hab hbc` 는 hab 와 hbc 를 차례로 적용해 `a = c` 를 도출한다.

이게 함수 호출 형태의 증명이다. `Eq.trans` 라는 정리가 사실 함수 — 두 등식 가설을 받아 새 등식을 돌려주는 함수이다. 우리가 hab, hbc 를 인수로 적용한다. exact 가 결과를 우리 목표와 매칭하고 통과한다.

학생들이 자주 묻는 의문 — "h.symm 같은 점 표기는 안 쓰나요?" 가능하다. `hab.trans hbc` 같이 점 표기로도 적을 수 있으며 같은 의미이다. 우리 코드는 명시적 함수 호출을 사용해 학생이 어떤 정리를 호출하는지 분명하게 한 것이다.

또 의문 — "constructor 두 번 쓰는 게 좀 어색해요." 대안이 가능하다. `refine ⟨?_, ?_, ?_⟩` 처럼 세 부 목표를 한 번에 만들거나, term 모드로 세 증명을 꺽쇠로 직접 적을 수도 있다. 다양한 방식이 있으며 우리 코드는 단계적·교육적이다.

수학적 의미 — 등호가 동치관계의 가장 단순한 예이다. 세 성질 (반사, 대칭, 추이) 모두 자명하게 만족한다.

블록 전체의 큰 그림. `Equiv1 (EqR A)` 라는 한 명제를 증명하는데 세 성질을 차례로 증명한다. 각 부 증명이 작은 example 이고 합쳐서 큰 정리가 된다. 모듈식 증명의 좋은 예이다.

## 블록 17 — `Le` 가 반대칭관계임을 증명

```lean
example : Antisymm Le := by
  -- 목표: ∀ a b, Le a b → Le b a → a = b
  intro a b hab hba
  -- hab : a ≤ b, hba : b ≤ a 가 되도록 Le 의 정의를 펼친다
  unfold Le at hab hba
  show a = b
  omega
```

반대칭성이다. 7 장의 부분순서관계의 토대이다.

`Antisymm` 정의를 펼치면 `∀ a b, R a b → R b a → a = b`. 양방향이면 같은 원소이다.

`intro a b hab hba` — 두 변수와 두 가설을 한 줄에 받는다. 가설 이름은 `hab` (a 와 b 사이의 R), `hba` (b 와 a 사이의 R) 이다.

`unfold Le at hab hba` — 두 가설에서 Le 정의를 펼친다. `Le a b` 가 `a ≤ b`, `Le b a` 가 `b ≤ a` 가 된다.

`show a = b` — 목표 명시.

`omega` — 두 부등식 가설 `a ≤ b` 와 `b ≤ a` 가 동시에 성립하면 `a = b` 이다. 부등식의 반대칭성 (자연수, 정수의 기본 사실) 이며 omega 가 자동 처리한다.

반대칭성과 비대칭성의 차이를 한 번 짚는다. 반대칭 (Antisymm) 은 `R a b ∧ R b a → a = b` — 양방향이면 같은 원소, 대각선 (a = b) 허용. 비대칭 (Asymm) 은 `R a b → ¬ R b a` — 한 방향이면 다른 방향 없음, 대각선 금지.

`Le` (≤) 는 반대칭이지만 비대칭은 아니다. `1 ≤ 1` 이 양방향이라도 (자기 자신) `a = a` 라 반대칭 조건을 만족한다. 그러나 비대칭은 `1 ≤ 1 → ¬ 1 ≤ 1` 인데 이는 모순이다. `<` (실제 작음) 는 비대칭이며 대각선이 없어 둘 다 만족한다. 비대칭이면 반대칭이지만 역은 성립하지 않는다.

학생들이 자주 묻는 의문 — "omega 가 정말 반대칭성을 안다고요?" omega 가 결정 알고리즘이다. `a ≤ b` 이고 `b ≤ a` 같은 가설들에서 `a = b` 같은 결론을 자동 도출한다. 산술적 보조정리들이 알고리즘 안에 내장되어 있어 학생이 신경 쓸 필요가 없다.

수학과 코드 대응.

| 수학 | Lean 4 |
|---|---|
| "a ≤ b 와 b ≤ a 가정" | `intro a b hab hba` 와 `unfold Le` |
| "보일 것은 a = b" | `show a = b` |
| "두 부등식 결합해 등식" | `omega` |

수학 한 줄 추론이 코드 한 전술이다.

## 블록 18 — 역관계 `Inv1` 과 여관계 `Compl1` 정의

```lean
variable {A : Type}

-- 역관계: a 와 b 의 자리를 바꾼다
def Inv1 (R : A → A → Prop) : A → A → Prop :=
  fun a b => R b a

-- 여관계: 관계의 부정
def Compl1 (R : A → A → Prop) : A → A → Prop :=
  fun a b => ¬ R a b
```

5.5 절의 두 연산을 Lean 4 로 옮긴다.

`variable {A : Type}` — 다시 변수 선언. 후속 정의들에서 A 가 자동이다.

### Inv1 — 역관계

`def Inv1 (R : A → A → Prop) : A → A → Prop := fun a b => R b a`

`Inv1` — Inverse (역) 의 줄임.

함수 본체 `fun a b => R b a` — 두 인수 a, b 를 받아 `R b a` 명제를 반환한다.

주목할 점은 인수 순서가 바뀐다는 것이다. 호출 `Inv1 R a b` 가 내부에서 `R b a` 가 된다. 곧 a 와 b 의 자리를 뒤집어서 R 에 넘긴다.

수학에서 $R^{-1} = \{(b, a) \mid (a, b) \in R\}$. 곧 모든 순서쌍의 자리 변경이다. Lean 4 의 `fun a b => R b a` 와 정확히 같다.

비유 — 친구 관계가 "내가 그를 친구로 둠" 이라면 역관계는 "그가 나를 친구로 둠" 이다. 같은 관계의 반대 관점이다.

### Compl1 — 여관계

`def Compl1 (R : A → A → Prop) : A → A → Prop := fun a b => ¬ R a b`

`Compl1` — Complement (여, 보완) 의 줄임.

함수 본체 `fun a b => ¬ R a b` — `R a b` 의 부정이다.

`¬` — 새 기호. 부정 (negation). 영어 "not", 한국어 "아니다". 키보드 `\not` 또는 `\neg`. 진술은 "다음 명제의 부정".

`¬ R a b` 의 의미는 "R a b 가 거짓" 또는 "(a, b) 가 R 에 없음" 이다.

내부 동작 — Lean 4 에서 `¬ P` 는 `P → False` 의 정의 등치이다. 곧 "P 라면 모순". 부정의 우아한 표현이다.

수학에서 $\overline{R} = (A \times A) \setminus R = \{(a, b) \mid (a, b) \notin R\}$. R 의 바깥이다. Lean 4 의 `fun a b => ¬ R a b` 와 같다.

두 정의의 공통점과 차이점. 공통은 둘 다 R 로부터 새 관계를 만드는 함수이고 둘 다 `A → A → Prop` 을 반환한다는 것이다. 차이는 Inv1 이 인수 순서를 변경하고 Compl1 이 부정한다는 것이다.

학생들이 자주 헷갈리는 함정이다. 이름이 비슷하지만 하는 일이 완전히 다르다. 한 번 더 강조하면 Inv 는 방향 뒤집기, Compl 은 멤버쉽 반전이다.

학생들이 자주 묻는 의문 — "그러면 Inv 와 Compl 이 같을 수도 있나요?" 일반적으로 다르다. 예외적·작위적 관계만 같으며 자연 관계에서는 서로 다른 결과이다.

또 의문 — "역관계와 여관계 외에 다른 관계 연산은?" 합집합 `R ∪ S`, 교집합 `R ∩ S`, 차 `R \ S` 등 집합 연산을 관계에 적용 가능하다. 또 합성 (Comp) 이 있다. 우리 코드는 가장 기본적인 두 가지만 다룬다.

또 한 가지 `¬ P` 의 정확한 의미. `¬ P` 는 `P → False` 이다. 곧 "P 가 참이라고 가정하면 모순 (False) 이 따라옴". 거짓의 정의이다. 직관은 "P 가 거짓" 이라는 것을 어떻게 증명하느냐인데, "P 가 참이라고 해 봐, 그러면 모순이지" 라는 논증이다. 일상적인 귀류법의 형식적 표현이다.

## 블록 19 — 역관계의 역관계는 자기 자신

```lean
example (R : A → A → Prop)
    (a b : A) :
    Inv1 (Inv1 R) a b ↔ R a b := by
  -- Inv1 (Inv1 R) a b
  --   = Inv1 R b a
  --   = R a b
  rfl
```

짧지만 매우 인상적인 증명이다.

`Inv1 (Inv1 R) a b` — 역관계의 역관계를 a, b 에 적용한다. 풀어 본다.

`Inv1 (Inv1 R)` — Inv1 함수를 Inv1 R 에 적용한다. 결과는 새 관계이다.

`Inv1 (Inv1 R) a b` — 그 새 관계를 a, b 에 적용한다.

정의를 두 번 펼치면 어떻게 되는가. `Inv1 R` 은 `fun a b => R b a`, 곧 인수를 뒤집어 R 에 넘기는 함수이다. `Inv1 (Inv1 R)` 은 `fun a b => (Inv1 R) b a`, 곧 인수를 뒤집어 Inv1 R 에 넘긴다. `(Inv1 R) b a` 는 `Inv1 R` 에 b, a 를 적용한 것이며 Inv1 R 정의를 펼치면 `(fun x y => R y x) b a` 가 `R a b` 이다.

종합하면 `Inv1 (Inv1 R) a b` 가 `R a b` 이다. 정의상 같다.

`:= by rfl` — 증명. 단 한 줄이다. 정의 등치의 강력한 표현이다. 양변이 글자 그대로 같으니 rfl 한 줄로 닫힌다.

수학적 의미 — "방향을 두 번 뒤집으면 원위치" 가 Lean 4 에서 "정의 두 번 펼치면 양변이 같음" 이다. 자명함의 정확한 형식적 표현이다.

학생들이 자주 묻는 의문 — "그러면 모든 자명한 사실이 rfl 로 닫히나요?" 정의상 동등한 사실만 닫힌다. 곧 양변이 계산만으로 글자 일치하는 경우이다. 정리를 호출해야 하는 사실은 안 된다. 예로 `R ∪ R = R` 같은 집합 합집합의 멱등성은 Lean 4 에서 정의 펼침만으로 안 되고 정리 호출 (`Set.union_self` 같은) 이 필요하여 `rfl` 이 안 된다.

또 의문 — "그러면 이중 부정 `¬ ¬ P ↔ P` 도 rfl 로 닫히나요?" Lean 4 의 기본 논리에서는 안 된다. 직관주의 논리 (intuitionistic logic) 에서 `¬ ¬ P → P` 가 자동이 아니다. 고전 논리 (classical logic) 의 추가 공리가 필요하다. 우리 역관계는 단순 인수 변경이라 정의 등치로 충분하다.

한 줄로 — 이 example 이 보여 주는 것은 "정의를 잘 만들면 핵심 정리가 자동으로 따라온다" 이다. 좋은 정의가 좋은 정리이다.

## 블록 20 — `R1`, `S1` 정의와 합성 예제

```lean
def R1 : Nat → Nat → Prop := fun a b => a = 1 ∧ b = 2
def S1 : Nat → Nat → Prop := fun a b => a = 2 ∧ b = 3

-- (1,3) 은 S∘R 에 있다: 중간 원소 2 를 거친다
example : Comp R1 S1 1 3 :=
  ⟨2, ⟨rfl, rfl⟩, ⟨rfl, rfl⟩⟩
```

합성의 비가환성을 보이기 위한 구체적 예제이다. 두 단순한 관계이다.

`R1` 정의 `fun a b => a = 1 ∧ b = 2`. 뜻은 "a = 1 이고 b = 2 인 두 자연수 쌍". 곧 관계 R1 은 단일 순서쌍 (1, 2) 만 포함하는 단순한 관계이다.

`S1` 정의 `fun a b => a = 2 ∧ b = 3`. 단일 순서쌍 (2, 3) 만 포함한다.

이렇게 단순하게 정의한 이유는 합성을 추적하기 쉽기 때문이다. R1 다음 S1 같은 결과가 손으로 명확히 보인다.

`example : Comp R1 S1 1 3 := ⟨2, ⟨rfl, rfl⟩, ⟨rfl, rfl⟩⟩`

`Comp R1 S1 1 3` — R1 다음 S1 의 합성을 1, 3 에 적용한다. (1, 3) 이 합성 관계에 속하는지 본다.

수학적으로 R1 의 (1, 2) 다음 S1 의 (2, 3) 이다. 중간 원소 2 가 매개한다. 따라서 (1, 3) 이 Comp R1 S1 에 속한다.

`:= ⟨2, ⟨rfl, rfl⟩, ⟨rfl, rfl⟩⟩` — 증명. term 모드이다. 이번엔 `by` 없이 직접 항을 적었다. 짧은 증명에 적합한 방식이다.

꺽쇠 분석. 목표 `Comp R1 S1 1 3` 의 정의를 펼치면 `∃ b, R1 1 b ∧ S1 b 3`. 꺽쇠 `⟨2, ⟨rfl, rfl⟩, ⟨rfl, rfl⟩⟩` 의 세 부분이다. `2` 는 증인 — b 자리에 2, "중간 원소가 2 이다". 첫 `⟨rfl, rfl⟩` 은 `R1 1 2` 의 증명이다. R1 1 2 의 정의를 펼치면 `1 = 1 ∧ 2 = 2` — 합접 두 부분이 각각 자명하므로 rfl 두 개로 닫고 꺽쇠로 묶는다. 둘째 `⟨rfl, rfl⟩` 은 `S1 2 3` 의 증명 — 같은 방식으로 `2 = 2 ∧ 3 = 3` 이다.

총 네 개의 rfl 이 두 합접의 양쪽을 닫는다. 모두 자명한 등식이다.

학생들이 자주 묻는 의문 — "왜 by 가 없나요?" 짧은 증명은 by 없이 term 모드가 더 깔끔하다. by 와 동등하지만 코드가 더 평탄하다. 우리 example 처럼 구조가 명확한 증명에 적합하다.

또 의문 — "꺽쇠가 자동으로 평탄화되는 거죠?" 그렇다. `⟨2, ⟨rfl, rfl⟩, ⟨rfl, rfl⟩⟩` 가 사실 `⟨2, ⟨⟨rfl, rfl⟩, ⟨rfl, rfl⟩⟩⟩` 의 줄임이다. 외층 ∃, 내층 ∧, 그 안에 두 합접의 ∧ — 네 단계 중첩이 자동 평탄화된다.

이 example 의 의미는 (1, 3) 이 R1 다음 S1 의 합성에 속함을 증명한 것이다. 짧지만 합성의 멤버쉽 증명의 표준 패턴이다.

## 블록 21 — 합성의 비가환성을 반례로

```lean
-- (1,3) 은 R∘S 에는 없다
example : ¬ Comp S1 R1 1 3 := by
  rintro ⟨b, ⟨h1, h2⟩, h3⟩
  omega
```

반대 방향의 합성이다. `Comp S1 R1` — S1 먼저, R1 다음. 합성의 순서를 바꾼다.

수학적으로 S1 의 (2, 3) 다음 R1 의 (1, 2) 인데, S1 의 끝점 3 과 R1 의 시작점 1 이 일치하지 않는다. 매칭이 안 된다. 따라서 (1, 3) 이 Comp S1 R1 에 속하지 않는다.

`¬ Comp S1 R1 1 3` — "(1, 3) 이 Comp S1 R1 에 속하지 않음" 이라는 부정 명제이다.

`:= by` — 전술 모드.

`rintro ⟨b, ⟨h1, h2⟩, h3⟩` — 부정 명제 증명의 핵심이다.

부정 증명의 일반 패턴. `¬ P` 가 `P → False` 이다. 곧 "P 를 가정하면 모순". 따라서 P 를 가정 (intro 또는 rintro) 하고 모순을 도출한다.

여기 P 는 `Comp S1 R1 1 3` 이며 `∃ b, S1 1 b ∧ R1 b 3` 이다.

`rintro ⟨b, ⟨h1, h2⟩, h3⟩` 가 P 를 가정하면서 동시에 분해한다. `b` 는 증인. `⟨h1, h2⟩` 는 `S1 1 b` 의 증명이며 S1 정의를 펼치면 `1 = 2 ∧ b = 3` 의 두 부분으로 `h1 : 1 = 2` 가 첫 부분, `h2 : b = 3` 이 둘째 부분이다. `h3` 는 `R1 b 3` 의 증명이며 R1 정의를 펼치면 `b = 1 ∧ 3 = 2` 이다.

여기서 `h1 : 1 = 2` 가 모순이다. `1 = 2` 가 거짓 — 자연수 1 과 2 가 다름이 자명하다. 그러나 가설로 들어와 있으면 모순이다. 모순 가정에서는 모든 명제가 따라온다 (ex falso quodlibet).

`omega` — 산술 모순을 자동 탐지한다. 가설에 `1 = 2` 같은 거짓 등식이 있으면 즉시 모순으로 처리한다. 결과로 `False` 가 도출되고, 그러면 우리가 증명해야 하는 어떤 목표든 자동으로 닫힌다.

InfoView 변화 — 전에는 `rintro` 후의 가설들, 후에는 `omega` 가 `1 = 2` 의 모순을 잡아 모든 부 목표를 닫는다.

이 증명의 의미는 `Comp S1 R1 1 3` 가 가정될 때 그 안의 가설들이 자체 모순이라는 것이다. 따라서 가정 자체가 성립 불가능하며 곧 부정 명제 `¬ Comp S1 R1 1 3` 가 참이다.

이게 반례 (counterexample) 증명이다. 영어 "counterexample", 한국어 "반례". 진술은 "보편 명제 (예로 합성이 가환) 를 부정할 때 구체 인스턴스로 반박".

두 example 종합 — `Comp R1 S1 1 3` 참, `¬ Comp S1 R1 1 3` 참. 곧 `Comp R1 S1` 과 `Comp S1 R1` 이 다르다. 합성이 비가환이다. 수학에서 합성의 비가환성을 반례 하나로 증명하는데 Lean 4 에서도 같은 패턴이다.

학생들이 자주 묻는 의문 — "omega 가 1 = 2 같은 모순을 어떻게 처리하나요?" omega 의 결정 알고리즘이 산술 모순 탐지를 포함한다. `1 = 2` 같은 수치적으로 명백한 거짓 등식을 즉시 잡아낸다. 결과로 그 어떤 목표든 닫힌다 (모순 가정에서 임의 결론).

또 의문 — "그러면 모든 모순이 omega 로 처리되나요?" 산술 모순만 처리한다. 비산술적 모순은 다른 전술 (`contradiction`, `exact absurd ...` 등) 이 필요하다. 우리 예제는 모순이 산술적이라 omega 이다.

## 블록 22 — 반사폐포와 대칭폐포 정의

```lean
variable {A : Type}

-- 반사폐포: R 에 항등관계를 합한다
def ReflClosure (R : A → A → Prop) : A → A → Prop :=
  fun a b => R a b ∨ a = b

-- 대칭폐포: R 에 역관계를 합한다
def SymmClosure (R : A → A → Prop) : A → A → Prop :=
  fun a b => R a b ∨ R b a
```

relation 의 마지막 절이다. 폐포 (closure) 두 가지를 다룬다.

먼저 `variable {A : Type}` — 다시 변수 선언이다.

### ReflClosure — 반사폐포

`def ReflClosure (R : A → A → Prop) : A → A → Prop := fun a b => R a b ∨ a = b`

`ReflClosure` — Reflexive Closure (반사폐포).

함수 본체 `fun a b => R a b ∨ a = b` — 두 인수 a, b 에 대해 새 명제를 반환한다.

`∨` — 새 기호. OR. 논리합. 영어 "or", 한국어 "또는". 키보드 `\or` 또는 `\vee`. 진술은 "두 명제 중 적어도 하나가 참".

`R a b ∨ a = b` — "(a, b) 가 원래 R 에 있거나, 아니면 a = b".

수학에서 $r(R) = R \cup I_A = R \cup \{(a, a) \mid a \in A\}$. 곧 "원래 R 의 쌍 또는 대각선 쌍". Lean 4 의 `R a b ∨ a = b` 와 1:1 대응한다. 집합 합집합 (∪) 이 명제 OR (∨) 에 대응한다. 두 개념이 본질적으로 같으며 멤버쉽 술어를 통해 변환된다.

### SymmClosure — 대칭폐포

`def SymmClosure (R : A → A → Prop) : A → A → Prop := fun a b => R a b ∨ R b a`

`SymmClosure` — Symmetric Closure (대칭폐포).

함수 본체 `fun a b => R a b ∨ R b a` — "(a, b) 가 R 에 있거나, (b, a) 가 R 에 있음".

수학에서 $s(R) = R \cup R^{-1}$. R 또는 역관계이다. `R b a` 가 역관계 쌍의 표현이며 인수 순서가 변경된다.

두 정의의 공통 구조는 둘 다 OR 형태라는 것이다. "원래 R 의 쌍 또는 추가 쌍" — 합집합의 명제 표현이다.

학생들이 자주 묻는 의문 — "그러면 추이폐포도 같은 방식으로 정의할 수 있나요?" 아니다. 더 복잡하다. 추이폐포는 무한 합집합 ($R \cup R^2 \cup R^3 \cup \cdots$) 이라 한 줄 정의가 불가능하다. 재귀적·귀납적 정의가 필요하다.

```lean
inductive TransClosure (R : A → A → Prop) : A → A → Prop
  | base : ∀ a b, R a b → TransClosure R a b
  | step : ∀ a b c, TransClosure R a b → R b c → TransClosure R a c
```

`inductive` 라는 키워드로 시작하는 새 정의 방식이다. 두 생성자 `base` 와 `step` 으로 추이폐포를 점진적으로 구성한다. 자세한 것은 후속 학습이다.

또 의문 — "Mathlib 에 표준 폐포 정의가 있나요?" 있다. `Relation.ReflGen`, `Relation.SymmGen`, `Relation.TransGen`, `Relation.EqvGen` 이다. 우리 정의는 학습용 단순화 버전이다.

또 의문 — "OR 의 정확한 내부 작동은?" Lean 4 의 OR 가 유도형으로 정의된다.

```
inductive Or (p q : Prop) : Prop
  | inl : p → Or p q
  | inr : q → Or p q
```

두 생성자는 `inl` (왼쪽이 참), `inr` (오른쪽이 참) 이다. OR 의 증명은 둘 중 하나를 선택한다. 다음 블록에서 활용한다.

## 블록 23 — 반사폐포가 R 을 포함함

```lean
example (R : A → A → Prop) (a b : A) (h : R a b) :
    ReflClosure R a b := by
  left
  exact h
```

짧지만 핵심적인 정리이다. "R 의 쌍은 반사폐포의 쌍이기도 하다."

`(h : R a b)` — 가설. (a, b) 가 R 에 속함이다.

`: ReflClosure R a b` — 결론. (a, b) 가 반사폐포에 속함이다.

`ReflClosure R a b` 의 정의를 펼치면 `R a b ∨ a = b`. OR 형태이다.

`:= by left` —

`left` — 새 전술. 영어 단어 그대로 "왼쪽". 한국어 "왼쪽". 진술은 "OR 목표의 왼쪽 부분을 선택해 증명한다". 대조로 `right` 는 "오른쪽 선택" 이다.

InfoView 변화 — 전에는 목표 `R a b ∨ a = b`, 후에는 목표 `R a b`. OR 의 왼쪽만 남는다.

`exact h` — 가설 h 가 정확히 `R a b` 이다. exact 가 매칭하고 닫는다.

세 줄로 끝난다. 매우 간단한 증명이다.

학생들이 자주 묻는 의문 — "왜 left 인가요? right 도 시도해 봐야 하나요?" 두 가지 모두 가능하나 우리 가설로 닫을 수 있는 게 left 이다. 만약 `right` 라면 목표가 `a = b` 인데 우리 가설 `h : R a b` 는 등식 `a = b` 가 아니므로 닫을 도구가 없다. `left` 면 목표 `R a b` 에 가설 h 가 정확히 그것이라 닫힌다. 곧 가설을 보고 적절한 분기를 선택하는 것이 일반적인 OR 증명의 전략이다.

또 의문 — "그러면 모든 OR 증명이 left 또는 right 으로 시작하나요?" 그렇다. OR 의 증명은 항상 두 분기 중 하나를 선택한다. 곧 left 또는 right 이다.

수학적 의미 — "(a, b) 가 R 에 속하면 (a, b) 가 R 에 속하거나 a = b" — 자명한 함의이다. 합집합의 멤버쉽 정의이다.

또 한 가지 — "term 모드로 더 짧게 적을 수 있나요?" 가능하다. `Or.inl h` 가 left 더하기 exact 의 풀이 형태이다.

```lean
example (R : A → A → Prop) (a b : A) (h : R a b) :
    ReflClosure R a b :=
  Or.inl h
```

세 줄이 한 줄로 더 압축적이 된다. `Or.inl` 은 OR 의 왼쪽 생성자 함수이며 `Or.inl h` 가 "h 를 사용해 OR 의 왼쪽 분기를 증명" 한다. 다양한 방식이 가능하며 상황에 따라 선택한다.

## 블록 24 — 대칭폐포가 대칭관계임

```lean
example (R : A → A → Prop) : Symm (SymmClosure R) := by
  intro a b h
  cases h with
  | inl hab =>
      right
      exact hab
  | inr hba =>
      left
      exact hba
```

마지막 example 이다. 대칭폐포가 정의대로 대칭관계임을 증명한다. 새 전술 `cases` 가 도입된다.

`Symm (SymmClosure R)` 의 정의를 펼치면 `∀ a b, SymmClosure R a b → SymmClosure R b a`.

`intro a b h` — 변수 둘, 가설 하나이다.

`h : SymmClosure R a b` 의 정의를 펼치면 `h : R a b ∨ R b a` — OR 형태의 가설이다.

목표 `SymmClosure R b a` 는 `R b a ∨ R a b` 이다. 또 OR 인데 인수 순서가 바뀌었다.

`cases h with` — 새 전술.

`cases` — 영어 단어 그대로 "경우". 한국어 "경우 분석". 진술은 "유도형 가설을 그 생성자별로 분해". OR 가설은 두 생성자 (`inl`, `inr`) 를 가지므로 `cases` 가 두 경우로 분해한다.

`| inl hab =>` — 첫 경우. 가설 h 가 `inl hab` 형태 (왼쪽 분기) 이며 hab 가 `R a b` 의 증명이다.

`| inr hba =>` — 둘째 경우. 가설 h 가 `inr hba` 형태 (오른쪽 분기) 이며 hba 가 `R b a` 의 증명이다.

`|` 가 패턴 매칭 표기이다. 함수형 언어의 표준. 영어 "pattern matching", 한국어 "패턴 매칭". OCaml, Haskell 같은 언어에서 자주 보는 표기이다.

각 경우의 증명.

### inl 경우

가설 `hab : R a b`. 목표 `R b a ∨ R a b`. 어느 분기를 선택하는가. hab 가 `R a b` 이고 목표의 오른쪽 부분이 정확히 `R a b` 이므로 `right` 를 선택한다.

`right` — OR 의 오른쪽 분기 선택. 목표가 `R a b` 로 변환된다.

`exact hab` — hab 가 정확히 `R a b` 이므로 닫힌다.

### inr 경우

가설 `hba : R b a`. 목표 `R b a ∨ R a b`. 목표의 왼쪽 부분이 `R b a` 이고 hba 와 일치하므로 `left` 를 선택한다.

`left` — 왼쪽 분기. 목표가 `R b a` 로 변환된다.

`exact hba` — 닫힌다.

두 경우 모두 닫힌다. 대칭폐포가 대칭관계임이 증명 완료된다.

수학적 의미 — 대칭폐포의 정의가 $R \cup R^{-1}$ 이다. 어떤 (a, b) 가 거기 있으면 (b, a) 도 거기 있다 (왼쪽이었으면 오른쪽으로, 오른쪽이었으면 왼쪽으로). 정확히 대칭성이다.

학생들이 자주 묻는 의문 — "cases 와 obtain 의 차이는?" 기능은 비슷하지만 cases 가 더 명시적이다. cases 는 각 경우의 이름을 패턴으로 명명하고, obtain 은 `obtain hab | hba := h` 같이 더 짧게도 가능하다. cases 표기가 각 경우가 무엇인지 즉시 보여서 가독성이 좋다.

또 의문 — "왜 inl, inr 인가요?" injection left, injection right 의 줄임이다. Or 의 두 생성자 이름이며 유도형의 표준 접두사이다. 다른 타입에서도 비슷하여 Sum 타입의 inl, inr 이 있다.

또 한 가지 — "cases ... with 외에 다른 표기는?" `match h with` 로 시작하는 직접 패턴 매칭도 가능하다. cases 가 전술 모드의 자연스러운 표현이다.

큰 그림. 우리 example 의 패턴은 OR 가설을 cases 로 분해하고, 각 경우에서 OR 목표의 적절한 분기를 left 또는 right 으로 선택하며, 가설을 exact 로 매칭하는 것이다. 이게 OR 가설과 OR 목표를 다루는 표준 패턴이며 relation 의 폐포 정리들에서 자주 등장한다.

## 블록 2 — 곱 타입과 순서쌍 정의

```lean
-- A × B 는 곱 타입. (a, b) 는 그 타입의 값이다.
def p : Nat × Nat := (3, 5)
```
먼저 첫 줄 `-- A × B 는 곱 타입. (a, b) 는 그 타입의 값.`.

두 개의 빼기 부호 `--` : Lean 4 의 주석 (comment) 기호. 

자, 둘째 줄. `def p : Nat × Nat := (3, 5)`

`def` — 영어 단어 "define" 의 약자. "정의한다" 라는 뜻

다음에 오는 `p` 가 새 이름.

비유 — 변수에 값을 넣는 것 같지만, 더 정확히는 "이름이 이 값을 가리키도록 약속"  

`p` — 우리가 새로 만드는 이름. 아무 이름이든. `a`, `myPoint`, `학생` 도 가능. 한글가능.

`: Nat × Nat` — 이게 타입 표기예요. 두 부분을 보자.

`:` — 콜론. "다음에 오는 게 이 이름의 타입이다" 라는 뜻. 수학 표기로 `p ∈ A` 와 비슷한 의미. "p 가 어떤 종류의 객체인지" 알려 주는 표시.

`Nat` — Natural number 의 약자. 자연수의 타입. Lean 4 에서는 0, 1, 2, 3, ... 모두 자연수. 0 도 포함. (이건 학파에 따라 다른데 Lean 은 0 포함파.) 

`×` — 키보드의 X 가 아니라 유니코드 곱셈 기호. 두 타입을 합쳐 곱 타입 (product type) 을 만드는 연산자. 수학의 곱집합 $A \times B$ 와 정확히 같음.   곱집합.

 `Nat × Nat` 의 의미 — "두 자연수의 곱집합 타입" 또는 "두 자연수의 쌍을 담는 타입". 수학 표기로 $\mathbb{N} \times \mathbb{N}$.
`\times` 를 치고 스페이스나 탭을 누르면 `×` 로 변환. 또는 `\x`가능. 

비슷한 패턴 — `\to` 가 `→`, `\and` 가 `∧`, `\or` 가 `∨`.

`:=` — 콜론 + 등호. "이 값이다" 라는 할당. 

`p : Nat × Nat := (3, 5)` 는 "p 는 자연수 두 개의 쌍이고, 그 값이 $(3, 5)$" 라는 한 줄의 약속.

`(3, 5)` —  순서쌍 (ordered pair) 표기. 수학에서 적는 그대로. 첫 자리에 3, 둘째 자리에 5.

 — Lean 4 가 `(3, 5)` 를 받으면 `Prod.mk 3 5` 라는 함수 호출로 해석. `Prod` 는 곱 타입의 이름, `mk` 는 "make (만들다)" 의 줄임말, 곧 곱 타입의 값을 만드는 생성자. 


```lean
-- 곱 타입은 세 개 이상으로도 중첩된다: Nat × Nat × Nat
def t : Nat × Nat × Nat := (3, 4, 27)
```

세 자연수의 쌍. `Nat × Nat × Nat` — 세 자연수의 곱 타입. 값은 `(3, 4, 27)`. 세 자리 각각 3, 4, 27.

 `Nat × Nat × Nat` 가 내부에서 `Nat × (Nat × Nat)` 로 해석. 

결과적으로 `(3, 4, 27)` 이 내부에서 `(3, (4, 27))` — 중첩된 두 순서쌍.

## 블록 3 — `.1`, `.2` 점 표기와 `rfl`

```lean
-- .1 은 첫째 성분, .2 는 둘째 성분을 꺼낸다.
example : p.1 = 3 := rfl
example : p.2 = 5 := rfl
```

`example` — 영어 단어 그대로 "예시". 이름 없는 정리. `def` 는 새 이름을 만들지만 `example` 은 이름 없이 그저 "이런 명제가 참" 임을 증명하고 끝. 학습용·시범용

언제 example 을 쓰는가 — 시범용. 

언제 def 를 쓰는가 — 나중에 재사용할 정리를 만들 때.

우리가 앞서 정의한 `p` 에 점 (`.`) 을 찍고 숫자 1 을 붙임. 의미는 "p 의 첫째 성분".

`p` 는 `(3, 5)` 라는 순서쌍. `p.1` 은 그 첫 자리, 곧 `3`. `p.2` 는 둘째 자리, 곧 `5`.

 Lean 4 의 곱 타입 `Prod` 는 1 부터 시작.  "첫째 성분", "둘째 성분" 이라 1 부터 씀

 — `.fst`: First (첫째), `.snd` : Second (둘째) 도 가능.
  `p.fst` = `p.1` 과 같고 `p.snd` = `p.2` 와 같음. 

자, `: p.1 = 3` 부분.

`:` — 다시 콜론. 이번에는 example 의 결론을 가리킴. "이 example 이 증명하는 명제는 `p.1 = 3` 이다" 라는 뜻.

`p.1 = 3` — 우리가 증명할 명제. "p 의 첫째 성분이 3 과 같다". 수학에서 적는 등식과 같음.

`= 3` 의 `=` 은 일상에서는 등호인데 Lean 4 에서는 "두 값이 같다" 라는 명제. 

결과는 참 또는 거짓. 곧 `p.1 = 3` 자체가 명제 — 참 명제이면 증명 가능, 거짓이면 불가능.

`:= rfl` — 증명. 이게 가장 중요.

`rfl` — 영어 단어 reflexivity (반사성) 의 줄임. 한국어로 "반사성", 약어 "rfl", 진술 "모든 객체는 자기 자신과 같다". 곧 임의의 $x$ 에 대해 $x = x$ 가 항상 참이라는 가장 기본적인 등식 사실.

자, `rfl` 이 어떻게 `p.1 = 3` 을 증명하는가. 

  - 좌변 `p.1` 을 평가하면 `(3, 5).1` 이 되고, 다시 평가하면 `3`. 우변은 `3`. 좌변과 우변 모두 `3` 으로 환원되었으니 글자 그대로 같음. `rfl` 이 통과.

이게 정의 등치 (definitional equality) 라는 개념. 영어 그대로 "정의에 의한 동등". 양변이 컴퓨터가 계산만 해서 글자 그대로 같아지면 `rfl` 한 줄로 증명 끝.


수학 표기와 Lean 4 표기의 대응을 표로 정리.

| 수학 | Lean 4 |
|---|---|
| $p = (3, 5)$ | `def p : Nat × Nat := (3, 5)` |
| 첫째 성분 | `p.1` |
| 둘째 성분 | `p.2` |
| $x = x$ 의 자명함 | `rfl` |

다음 블록으로.

## 블록 4 — 순서쌍 상등 정리 (`Prod.mk.injEq`)

```lean
example (a c b d : Nat) :
    ((a, b) = (c, d))
      ↔ (a = c ∧ b = d) := by
  -- 정의에 해당하는 정리로 재서술
  rw [Prod.mk.injEq]
```


`example (a c b d : Nat)` — 

`(a c b d : Nat)` — 괄호 안에 네 개의 이름과 한 번의 타입 표기. 의미 — "a, b, c, d 네 개가 자연수다." 한 번에 네 변수의 타입을 적은 줄임 표기.

수학적으로 — "임의의 자연수 a, b, c, d 에 대해" 라는 의미. 이 example 은 모든 자연수 조합에 대해 성립할 명제를 증명할 예정.

자, 다음 줄 `: ((a, b) = (c, d)) ↔ (a = c ∧ b = d) := by`.

`((a, b) = (c, d))` — 두 순서쌍의 상등. 좌변 순서쌍 $(a, b)$ 와 우변 순서쌍 $(c, d)$ 가 같다는 명제.

`↔` — 새 기호. 양방향 화살표. 영어로 "if and only if", 줄임 "iff", 한국어로 "필요충분조건" 또는 "동치". 진술 — "양쪽이 동시에 참이거나 동시에 거짓".

키보드 입력 — `\iff` 또는 `\<->` 를 치고 스페이스. `↔` 로 변환.

수학에서 자주 보는 그 기호죠. $A \iff B$ 와 같음.

`(a = c ∧ b = d)` — 두 등식의 합접.

`∧` — 새 기호. AND, 그리고. 두 명제가 동시에 참. 키보드 `\and` 또는 `\wedge`.

`a = c ∧ b = d` 의 의미 — "a 가 c 와 같고 동시에 b 가 d 와 같다".

 전체 명제 — "두 순서쌍이 같다 ↔ 첫째 성분이 같고 둘째 성분이 같다." 수학에서 배운 순서쌍 상등의 정의 그대로. relation 의 핵심 정리 중 하나.

`:= by` — 이번엔 `:= rfl` 이 아니에요. `:= by` 로 시작합니다.

`by` — 영어 단어 그대로 "by ~으로". 전술 모드 (tactic mode) 의 진입 키워드. 

전술 모드 — 영어로 **tactic mode. 증명을 한 번에 적지 않고 단계적으로 만들어 가는 방식**. 마치 칠판에 한 줄씩 적으며 증명하는 것처럼. Lean 4 의 가장 자주 쓰는 증명 방식.

대조 — 직접 모드 (term mode). 증명을 한 줄에 함수처럼 적는 방식. 짧은 증명에 적합. 우리 슬라이드 3 의 `:= rfl` 이 그 예.

`:= by` 다음에는 — 전술들의 나열. 한 줄에 하나씩.

`-- 정의에 해당하는 정리로 재서술` — 주석. 사람이 읽으라고 적은 메모. 다음 줄의 의도를 설명.

`rw [Prod.mk.injEq]` — 이게 증명의 본체. 한 줄.

  * `rw` — 영어 단어 rewrite (다시 쓰다) 의 줄임. 한국어로 "재작성", 약어 "rw", 진술 "정리를 사용해 목표나 가설을 다시 쓴다".

  * `rw [정리이름]` 가 작동하는 방식 — Lean 4 가 주어진 정리의 좌변과 일치하는 부분을 목표에서 찾아 우변으로 치환. 또는 동치 정리라면 두 형태가 호환.

  * `Prod.mk.injEq` — 정리의 이름. 세 부분.

  * `Prod` — 곱 타입의 이름.

  * `mk` — Make (만들다) 의 줄임. 곱 타입의 생성자.

  * `injEq` — Injection equality (단사 등식) 의 줄임. "생성자가 단사 함수이므로 등식이 성분별로 분해된다" 는 정리.

  * 전체 — "Prod 타입의 mk 생성자의 단사성 등식". 시그너처 (정리의 모양) 가 정확히

```
Prod.mk.injEq : ((a, b) = (c, d)) ↔ (a = c ∧ b = d)
```

 그래서 `rw [Prod.mk.injEq]` 한 줄로 닫힘.

- `rw` 가 목표 `((a, b) = (c, d)) ↔ (a = c ∧ b = d)` 의 좌변과 `Prod.mk.injEq` 의 좌변을 비교 — 같음. 

우변으로 치환 — 우리 목표의 우변과 일치. 양변 일치. 자동 닫힘.

InfoView 변화 — 화면 오른쪽의 정보 창에서 보이는 변화. 전 — 목표 `((a, b) = (c, d)) ↔ (a = c ∧ b = d)`. 후 — `No goals` (목표 없음). 한 줄로 끝.

## 블록 5 — 예제 5-2 방정식 풀이

```lean
example (x y : Int)
    (h : ((2*x + 1, (5:Int)) = (7, y + 3))) :
    x = 3 ∧ y = 2 := by
  -- (1) 순서쌍 상등으로 성분별 등식 두 개를 얻는다
  rw [Prod.mk.injEq] at h
  -- 이제 h : 2*x + 1 = 7 ∧ 5 = y + 3
  obtain ⟨h1, h2⟩ := h
  -- (2) 각 성분의 결론을 산술로 닫는다
  constructor
  · omega
  · omega
```


`example (x y : Int)` — 두 변수 x, y 가 정수.

`Int` — Integer (정수) 의 줄임. 자연수 `Nat` 와 다른 타입. Lean 4 에서는 0, 음수, 양수 모두 포함하는 정수 타입.

**`Nat` 가 아니라 `Int` 인가요?**

답 — 예제의 답을 보면 y = 2 인데, 정수 풀이에서는 음수 답이 나올 가능성도 있어요. `Nat` 는 음수가 안 되므로 더 일반적인 `Int` 를 씁니다. 또 산술 풀이에 자유로움을 주기 위해.

`(h : ((2*x + 1, (5:Int)) = (7, y + 3)))` — 가설.

`h` — 가설의 이름. h 는 hypothesis (가설) 의 줄임. 관습적으로 가설은 `h`, `h1`, `h2`, `hab` 같이 짓습니다.

`:` 다음 — 가설의 내용. `((2*x + 1, (5:Int)) = (7, y + 3))`. 두 순서쌍이 같다는 가정.

여기 `(5:Int)`  Lean 4 에서 숫자 리터럴 `5` 는 문맥에 따라 자연수일 수도, 정수일 수도, 실수일 수도 있음. 타입 추론기가 문맥을 보고 결정. 그런데 순서쌍 `(2*x + 1, 5)` 와 `(7, y + 3)` 에서 — `2*x + 1` 이 정수 (x 가 정수니까), `y + 3` 도 정수 (y 가 정수니까). 따라서 둘째 자리의 `5` 도 정수여야 양변 타입이 일치.

만약 `:Int` 를 안 적으면 — Lean 4 가 자연수로 추론할 수도 있고, 그러면 타입 충돌. 컴파일 오류. 그래서 명시적으로 `(5:Int)`.

**헷갈리는 부분** — "5 는 그냥 5 아닌가? 왜 타입을 명시?". — Lean 4 가 다양한 수 체계를 다루므로 정확한 타입을 알려야. 작은 불편이지만 안전.

`: x = 3 ∧ y = 2` — 결론. "x 가 3 이고 y 가 2". 합접.

`:= by` — 전술 모드 진입. 우리가 익숙해진 그것.

이제 본격 증명. 네 줄.

`rw [Prod.mk.injEq] at h` — 

블록 4 에서 본 `rw [Prod.mk.injEq]` 와 비슷한데 끝에 `at h` 가 추가

`at h` — "h 라는 위치에서". 곧 `rw` 를 목표에서가 아니라 가설 h 에서 적용. 

블록 4 의 `rw [Prod.mk.injEq]` — 목표를 다시 씀.

여기의 `rw [Prod.mk.injEq] at h` — 가설 h 를 다시 씀.

방향 — Lean 4 가 자동 처리. 가설이 순서쌍 등식 형태이므로 → 성분별 등식의 합접으로 변환.

InfoView 변화 — 전 — `h : (2*x + 1, 5) = (7, y + 3)`. 후 — `h : 2*x + 1 = 7 ∧ 5 = y + 3`. 가설이 합접으로 변환.

`obtain ⟨h1, h2⟩ := h` — 다음 전술.

`obtain` — 영어 단어 그대로 "얻다, 입수하다". 복합 명제를 분해해 작은 가설들을 얻는 전술.

`⟨h1, h2⟩` — 꺽쇠 표기. 새 기호.

`⟨` 와 `⟩` 가 일반 괄호 `<>` 와 비슷하지만 다른 기호. 키보드 `\<` 와 `\>`. 또는 `\langle` 와 `\rangle`.

꺽쇠의 의미 — 안에 든 것을 그 자리에서 분해 또는 묶음. 여기서는 분해.

`obtain ⟨h1, h2⟩ := h` 가 하는 일 — h 가 합접 `A ∧ B` 형태일 때, h 를 두 부분 `h1 : A` 와 `h2 : B` 로 분해. 원래 `h` 는 사라지고 두 새 가설 등장.

InfoView 변화 — 전 — `h : 2*x + 1 = 7 ∧ 5 = y + 3`. 후 — `h1 : 2*x + 1 = 7`, `h2 : 5 = y + 3`. 합접이 두 가설로 풀림.

학생들이 자주 묻는 의문 — "꺽쇠 안에 이름이 두 개인 이유는?"

답 — 분해된 두 부분에 각각 이름을 붙이려고. h1 이 첫째 부분, h2 가 둘째 부분. 이름은 자유 — h1, h2 대신 left, right 같은 이름도 가능. 우리는 관습적으로 h1, h2.

### 다음 줄 `constructor` —

`constructor` — 영어 단어 그대로 "생성자". 결론이 합접일 때 그 합접의 생성자를 적용해 두 부 목표로 분해.

자, `obtain` 과 `constructor` 의 차이를 짚어요.

`obtain ⟨...⟩ := h` — 가설의 합접을 분해.

`constructor` — 목표의 합접을 분해.

대칭적인 두 전술. 가설과 목표 양쪽에서 합접을 다루는 도구.

InfoView 변화 — 전 — 목표 `x = 3 ∧ y = 2`. 후 — 두 부 목표. (1) `x = 3`, (2) `y = 2`. 한 목표가 둘로.

수학에서 — "A 그리고 B 를 보이려면 A 를 보이고 또 B 를 보인다" 의 정확한 대응. 목표를 둘로 나눠 각각 따로 증명.

다음 줄 `· omega` —

`·` — 가운데 점 (centered dot). 키보드 입력 `\.` 또는 `\cdot`. 자주 쓰는 기호.

의미 — 부 목표 시작 표시. `constructor` 가 두 부 목표를 만들었으므로, 각각에 대해 `·` 로 시작해 증명을 분리해 적음.

`omega` — 새 전술. 

영어로 "omega". 한국어로도 "오메가". 약어가 아닌 그리스 문자 이름 그대로. 진술 — "선형 정수 산술 (linear integer arithmetic) 의 결정 알고리즘".

**선형 정수 산술 — 덧셈, 뺄셈, 상수와 변수의 곱, 부등식, 등식만으로 표현되는 정수 식. 변수 두 개의 곱 (예 — x · y) 같은 비선형은 제외**.

**omega 가 하는 일 — 가설과 목표를 종합해 자동으로 산술적 결론을 도출. 1990 년대 William Pugh 가 도입한 알고리즘. Lean 4 의 Mathlib 가 그 구현체**.

우리 첫 부 목표 — `x = 3`. 사용 가능한 가설 — `h1 : 2*x + 1 = 7`. omega 가 `h1` 을 사용해 `2*x = 6 → x = 3` 을 자동 유도. 부 목표 닫힘.

둘째 부 목표 `· omega` — 같은 일을 둘째 부 목표 `y = 2` 에 대해. 가설 `h2 : 5 = y + 3` 에서 `omega` 가 `y = 2` 를 도출.

### omega 가 무엇이든 자동 풀어 주는가?

 선형 정수 산술만. 비선형 (`x * y` 같은 두 변수의 곱) 은 불가. 그때는 `nlinarith` (nonlinear linear arithmetic) 같은 다른 전술 필요. 우리 예제는 완전히 선형이라 `omega` 가 즉시 해결.

### "왜 `omega` 가 그렇게 강력한가요?"

 선형 정수 산술이 결정 가능 (decidable). 곧 모든 참 명제를 알고리즘이 항상 찾아낼 수 있는 영역. 1929 년 Mojżesz Presburger 가 증명. omega 가 그 결정 알고리즘의 구현. "수학자가 손으로 푸는 모든 선형 부등식 사슬을 0.1 초에" — 자동화의 정점.

## 수학 풀이와 Lean 4 코드의 1:1 대응.

| 수학 풀이 | Lean 4 코드 |
|---|---|
| "순서쌍 상등을 풀어 쓰면" | `rw [Prod.mk.injEq] at h` |
| "첫 성분 등식과 둘째 성분 등식" | `obtain ⟨h1, h2⟩ := h` |
| "결론도 두 부분으로 나누어" | `constructor` |
| "첫째에서 x = 3" | `· omega` |
| "둘째에서 y = 2" | `· omega` |

수학의 다섯 단계가 코드의 다섯 줄. 형식 증명의 미.

또 의문 — "두 부 목표 모두 omega 인데, 한 번에 처리할 수 없나요?"

답 — 가능. `<;> omega` 라는 단축 표기. "세미콜론 두 개" 가 "모든 부 목표에 같은 전술 적용". 그러나 명시성을 위해 우리는 두 번 따로 적었어요. 학습 단계에서는 명시가 좋음.

## 블록 6 — 관계 정의 `Le`

```lean
-- 관계: 두 인수를 받아 명제를 돌려주는 함수
def Le : Nat → Nat → Prop := fun a b => a ≤ b
```

`def Le` — 새 이름 `Le` 의 정의. Le 는 영어 "less than or equal" 의 머리글자.

`: Nat → Nat → Prop` — 타입. 새 기호 두 개.

`→` — 화살표. 영어 단어 "to", 한국어 "에서 ~로". 함수 타입을 만드는 기호. 키보드 `\to` 또는 `\->`.

`A → B` 의 의미 — "A 에서 B 로 가는 함수의 타입". 곧 A 를 입력으로 받아 B 를 출력하는 함수들의 모임.

자, 그러면 `Nat → Nat → Prop` 의 의미는?



Lean 4 의 `→` 는 오른쪽 결합 (right-associative). 곧 `Nat → Nat → Prop` 가 내부에서 `Nat → (Nat → Prop)` 로 해석.

뜻 — "자연수 하나를 받아, (자연수에서 명제로 가는 함수) 를 돌려주는 함수". 곧 함수가 두 자연수를 차례로 받아 명제를 돌려줌.

이런 방식이 Curry 화 (currying). 영어 "currying", 한국어 "커리화". 하스켈 커리 (Haskell Curry) 라는 수학자의 이름에서 옴. 다중 인수 함수를 단일 인수 함수의 연속으로 표현하는 기법. Lean 4, Haskell, OCaml 등 함수형 언어의 표준.

`Prop` — 새 타입. 영어 "proposition" 의 줄임. 한국어 "명제". 진술 — "참 또는 거짓인 주장의 타입".

자, 그러면 `Nat → Nat → Prop` 전체는 — "두 자연수를 받아 명제를 돌려주는 함수의 타입". 정확히 "두 자연수 사이의 관계" 를 표현하는 타입.

비유 — `Le a b` 가 "a 와 b 가 부등식 a ≤ b 라는 관계에 있다" 라는 명제. 명제이므로 참 또는 거짓.



### 연결고리 — 멤버쉽 술어 (membership predicate). 

집합 S 에 대해 $\chi_S(x) = (x \in S)$ 가 특성 함수. 이 특성 함수가 "x 가 집합 안에 있는가" 를 명제로 답함. 정확히 두 표현의 다리.

Lean 4 가 함수 표현을 선택한 이유 — 함수가 계산에 더 자연스러움. 부분 적용 (partial application), 합성, 람다 등 도구가 풍부. 집합 자체는 계산 도구가 더 적음.

`:= fun a b => a ≤ b` — 함수 본체.

`fun` — 람다 함수 (lambda function) 의 키워드. 영어 단어 그대로. 한국어 "익명 함수" 또는 그냥 "fun". 진술 — "이름 없는 함수를 만드는 도구".

`fun a b =>` — "두 인수 a, b 를 받아". 이 부분이 함수의 입력 자리.

`=>` — 화살표. "그 결과는". 키보드 `=>` 그대로 두 글자 입력하면 자동 변환되거나, 또는 `\Rightarrow` 입력.

`a ≤ b` — 결과. "a 가 b 이하" 라는 명제.

`≤` — 부등식 기호. 작거나 같음. 키보드 `\le` 또는 `\leq`. 수학에서 보는 그 기호.

전체 의미 — "두 자연수 a, b 를 받아 a ≤ b 라는 명제를 돌려주는 함수가 Le 이다."

곧 `Le 1 3` 을 평가하면 결과는 `1 ≤ 3` 이라는 명제. 그 명제가 참인지 거짓인지는 또 다른 문제 (당연히 참).

학생들이 자주 묻는 의문 — "수학에서는 그냥 ≤ 가 있는데 왜 굳이 새로 Le 를 정의하나요?"

답 — 교육용. Mathlib 에 이미 `≤` 가 정의되어 있으므로 실용적으로는 새 Le 가 필요 없음. 그러나 "관계가 어떻게 함수로 표현되는지" 를 학생에게 명시적으로 보이기 위해 우리가 새 정의를 만듦. 

실전 코드에서는 Mathlib 의 `≤` 를 그대로 사용.

또 한 가지 — `def Le (a b : Nat) : Prop := a ≤ b` 처럼도 쓸 수 있음. 두 표기가 완전히 동등. 우리 슬라이드 형태가 람다로 본체를 정의하는 형태. 함수의 본질을 보여 줘서 학습에 좋음.

다음 블록에서 이 Le 를 실제로 사용.

## 블록 7 — `Le 1 3` 의 증명

```lean
-- a R b 는 Lean 에서 R a b 로 쓴다.
example : Le 1 3 := by
  show 1 ≤ 3
  omega
```

자, Le 를 실제로 사용. "1 이 3 이하" 라는 사실을 Lean 4 로 증명.

`Le 1 3` — 함수 호출. 함수 `Le` 에 두 인수 `1` 과 `3` 을 차례로 적용. 결과는 명제 `1 ≤ 3`.

자, 함수 호출 표기에 주목. Lean 4 에서 함수 적용은 공백으로 표현. `Le(1, 3)` 같이 괄호를 쓰지 않아요. 그냥 `Le 1 3`. 함수 이름 다음 공백, 첫 인수, 공백, 둘째 인수.

이게 함수형 프로그래밍의 표준 표기. Python, C 와는 다른 스타일. 처음에 낯설지만 곧 익숙해집니다.

수학 표기와의 대응 — 수학에서 $a\ R\ b$ 또는 $(a, b) \in R$. Lean 4 에서 `R a b`. 공백 하나의 차이. 

`example : Le 1 3 := by` — "Le 1 3 이라는 명제를 증명한다" 라는 example. by 로 전술 모드.

`show 1 ≤ 3` — 새 전술.

`show` — 영어 단어 그대로 "보이다, 명시하다". 한국어 "명시". 진술 — "현재 목표를 같은 의미의 다른 형태로 다시 적는다".

지금 목표가 `Le 1 3`. Le 의 정의를 펼치면 — `Le 1 3` 가 `(fun a b => a ≤ b) 1 3` 이 되고, 평가하면 `1 ≤ 3`. 곧 `Le 1 3` 과 `1 ≤ 3` 이 정의상 동등 (definitionally equal).

`show 1 ≤ 3` 가 하는 일 — "지금 보이려는 게 사실 1 ≤ 3 이다" 라고 명시적으로 알림. Lean 4 가 두 형태의 동등성을 확인하고 목표를 새 형태로 변환.

InfoView 변화 — 전 — 목표 `Le 1 3`. 후 — 목표 `1 ≤ 3`. 시각적으로 더 명확.

학생들이 자주 묻는 의문 — "그럼 show 는 꼭 필요한가요? 안 적어도 되나요?"

답 — 대부분 안 적어도 됨. 다음 전술 `omega` 가 자동으로 정의를 펼침. 그러나 명시성을 위해 적었어요. 학습 단계에서는 "지금 무엇을 증명하고 있는지" 를 매번 명시하는 게 좋음.

`omega` — 우리가 블록 5 에서 본 그 전술. 선형 정수 산술의 결정 알고리즘.

목표 `1 ≤ 3` 가 자명. omega 가 즉시 닫음. 0.001 초.

자, 이 짧은 example 의 핵심 — "관계가 함수처럼 호출되고, 그 함수의 결과 명제가 증명 가능". 종이에 적은 "1 R 3" 이 Lean 4 의 "Le 1 3" 으로 그대로 옮겨짐. 

수학과 코드의 1:1 대응 한 줄 — `a R b` ↔ `R a b`.

## 블록 8 — 항등관계 `IdRel`

```lean
-- 항등관계
def IdRel (A : Type) :
    A → A → Prop :=
  fun x y => x = y

-- 모든 x 에 대해 x 는 자기 자신과 항등관계에 있다
example (x : Nat) :
    IdRel Nat x x := by
  show x = x
  rfl
```

자, 이번엔 항등관계 (identity relation). 모든 원소가 자기 자신하고만 관계 맺는 가장 단순한 관계.

`def IdRel (A : Type) : A → A → Prop := fun x y => x = y` — 정의.

`IdRel` — Identity Relation 의 줄임. 항등관계.

`(A : Type)` — 새 인수. 명시 인수 (explicit argument).

`A` — 타입의 이름. 대문자로 적는 게 관습. 우리가 어떤 타입 위에서 항등관계를 정의할지 그 자리에 두는 표시.

`: Type` — A 의 타입이 `Type`.

`Type` — 새 키워드. "타입의 타입". Lean 4 에서는 모든 것이 타입을 가지는데, 자연수의 타입은 `Nat`, 정수의 타입은 `Int`, 명제의 타입은 `Prop`. 그러면 `Nat` 자체의 타입은? 답 — `Type`. 곧 "타입들이 모인 우주".

이게 우주 계층 (universe hierarchy) 의 개념. 영어 "type universe", 한국어 "타입 우주". 진술 — "타입의 타입을 표현하는 메타 단계".

학생들이 자주 묻는 의문 — "그러면 Type 의 타입은 또 있나요?"

매우 좋은 질문. 답 — `Type 1`. 그 위는 `Type 2`. 무한히 올라가요. `Type 0` 이 보통 우리가 쓰는 `Type`. 이걸 가지고 러셀의 역설 같은 모순을 피하는 게 우주 계층의 역할. 깊은 주제이지만 실용에서는 그냥 `Type` 만 알면 충분.

자, 그러면 `(A : Type)` 의 의미 — "어떤 타입 A 를 명시 인수로 받음". 호출할 때 우리가 직접 적어 줘야 함.

`: A → A → Prop` — 반환 타입. "A 위의 관계 (A 와 A 사이의 관계)". 

`:= fun x y => x = y` — 함수 본체. 두 인수 x, y 에 대해 명제 `x = y` 를 돌려줌.

수학의 항등관계 정의 — $I_A = \{(x, x) \mid x \in A\}$. 곧 "x 와 y 가 항등관계에 있다 ↔ x 와 y 가 같음". Lean 4 표현 `fun x y => x = y` 와 정확히 같음.

`= ` — 등호. 두 객체가 같다는 명제. 결과가 명제 (`Prop` 타입). 

자, 두 번째 example.

`example (x : Nat) : IdRel Nat x x := by` — 

`(x : Nat)` — 임의의 자연수 x.

`IdRel Nat x x` — 함수 호출. `IdRel` 에 세 인수 `Nat`, `x`, `x` 차례로 적용. 

자, 인수 세 개에 주목. 첫 인수 `Nat` 가 우리가 항등관계를 정의할 타입. 둘째와 셋째 `x, x` 가 관계의 두 원소.

평가하면 — `IdRel Nat` 가 자연수의 항등관계 함수. 그 함수에 `x, x` 적용. 결과는 명제 `x = x`.

— "왜 `IdRel x x` 가 아니라 `IdRel Nat x x` 인가?"

 — `IdRel` 정의에서 `(A : Type)` 가 명시 인수였기 때문. 명시 인수는 호출 시 반드시 적어야 함. 그래서 첫 자리에 타입 `Nat`

대안 — 만약 `{A : Type}` (중괄호) 라고 정의했다면 암묵 인수. 호출 시 생략 가능. 

`:= by` — 전술 모드.

`show x = x` — 목표를 명시. `IdRel Nat x x` 가 정의상 `x = x` 와 같음. show 가 시각적으로 명시.

`rfl` — 우리가 익숙한 그 전술. `x = x` 가 자명. rfl 이 닫음. 0.001 초.

수학적 의미 — "모든 자연수 x 에 대해 x 가 자기 자신과 항등관계에 있다." 이게 항등관계의 가장 기본적인 성질. 모든 원소가 자기와 관계.


 — 항등관계는 모든 관계 성질 (반사·대칭·추이) 을 자명히 만족.   
반사성 — `x = x`. 대칭성 — `x = y → y = x`. 추이성 — `x = y, y = z → x = z`. 

모두 등호의 기본 성질. 그래서 항등관계가 동치관계의 가장 단순한 예. relation 의 5.4 절에서 다루는 그 관계.

"왜 `Nat` 만 쓰나요? 다른 타입에서도 IdRel 이 작동하나요?"

 `IdRel Int`, `IdRel String`, 또는 우리가 정의한 어떤 타입에서도. `(A : Type)` 가 다형성 (polymorphism). 모든 타입에 통하는 일반적 정의.

## 블록 9 — 관계 합성 `Comp` 와 `RPow2`

```lean
-- 합성: a 에서 b 로 R, b 에서 c 로 S 면, a 에서 c 로 S∘R
def Comp {A : Type} (R S : A → A → Prop) :
    A → A → Prop :=
  fun a c => ∃ b, R a b ∧ S b c

-- R 의 제곱: R 을 두 번 합성
def RPow2 {A : Type} (R : A → A → Prop) :
    A → A → Prop :=
  Comp R R
```

자, 이번엔 합성 (composition). relation 의 5.5 절에서 다룬 그 연산.

`def Comp {A : Type} (R S : A → A → Prop) : A → A → Prop := fun a c => ∃ b, R a b ∧ S b c`

먼저 새 표기 — `{A : Type}`.

`{` 와 `}` 가 중괄호. 명시 인수의 `(` 와 다른 표기.

`{A : Type}` — 암묵 인수 (implicit argument). 영어 "implicit argument", 한국어 "암묵 인수". 진술 — "호출 시 적지 않아도 Lean 4 가 문맥에서 자동 추론한다".

대조 — 명시 인수 `(A : Type)` 는 호출 시 반드시 적어야. 암묵 인수 `{A : Type}` 는 생략.

왜 여기서 암묵을 쓰는가 — `Comp R S` 라는 호출에서 R 과 S 의 타입이 `A → A → Prop`. Lean 4 가 R, S 의 타입을 보고 A 를 자동 추론 가능. 매번 `Comp Nat R S` 처럼 타입을 명시할 필요 없음. 편의.

학생들이 자주 묻는 의문 — "그러면 IdRel 도 암묵으로 하면 안 되나요?"

좋은 시도. 답 — IdRel 호출에서 `IdRel x x` 라고 적으면 — x 의 타입에서 A 를 추론 가능. 가능. 다만 우리 슬라이드 8 에서는 학습용으로 명시. 실전에서는 암묵이 더 자연스러움. 

`(R S : A → A → Prop)` — 두 명시 인수. 두 관계 R, S.

자, 한 괄호 안에 R 과 S 가 같이 있는 게 줄임 표기. `(R : A → A → Prop) (S : A → A → Prop)` 와 동등하지만 짧음.

`: A → A → Prop` — 반환 타입. 합성도 관계.

`:= fun a c => ∃ b, R a b ∧ S b c` — 함수 본체. 가장 중요한 부분.

`fun a c =>` — 두 인수 a, c 를 받음. 합성 관계의 두 원소.

`∃ b,` — 새 기호. 

`∃` — 존재 양화사 (existential quantifier). 영어 "there exists", 한국어 "존재한다". 키보드 `\exists` 또는 `\ex`. 진술 — "어떤 b 가 존재해서 그 조건을 만족".

`∃ b, P` 의 의미 — "P 조건을 만족하는 b 가 적어도 하나 존재한다".

수학에서 보는 그 기호. $\exists b$ 와 같음.

`R a b ∧ S b c` — 조건. AND 두 명제. 

`R a b` — a 와 b 가 관계 R 에 있음.

`S b c` — b 와 c 가 관계 S 에 있음.

`∧` — AND. 우리가 본 그 기호.

전체 — "어떤 b 가 존재해서 `R a b` 와 `S b c` 가 둘 다 성립한다."

이게 합성의 정의. relation 5.5 절에서 — $S \circ R = \{(a, c) \mid \exists b : (a, b) \in R \wedge (b, c) \in S\}$. 정확히 같은 정의.

자, 주의해야 할 표기 순서. 수학에서 `S ∘ R` 의 의미는 "R 먼저, S 다음". 오른쪽이 먼저 적용. 함수 합성의 관례. Lean 4 의 `Comp R S` — 함수 인수 순서 그대로, "R 이 첫 인수, S 가 둘째".

자, "R 먼저, S 다음" 의 의미가 두 표기에서 같은지 확인. `Comp R S a c` 의 정의 — `∃ b, R a b ∧ S b c`. 곧 a 에서 R 로 b 까지 가고, b 에서 S 로 c. R 먼저, S 다음. 수학의 $S \circ R$ 와 같은 의미. 표기만 다를 뿐.

학생들이 자주 묻는 의문 — "왜 수학 표기랑 Lean 표기가 순서가 반대처럼 보이나요?"

답 — 수학 표기 $S \circ R$ 는 "함수 적용 관례" 에 따른 것. $f(g(x)) = (f \circ g)(x)$ 처럼 왼쪽이 나중. Lean 의 `Comp R S` 는 "함수 인수 순서" 에 따른 것 — 왼쪽 인수가 먼저. 둘 다 같은 합성을 다른 관점에서 표기한 것.

`def RPow2 {A : Type} (R : A → A → Prop) : A → A → Prop := Comp R R`

`RPow2` — R 의 2 거듭제곱 (R Power 2). 

`Comp R R` — R 을 자기 자신과 합성. 곧 길이 2 경로의 관계. relation 5.3 절의 $R^2$.

짧은 정의지만 의미 깊음. R 의 거듭제곱이 Lean 4 에서 합성의 반복으로 표현. 수학에서 $R^2 = R \circ R$ 가 코드의 `Comp R R`.

학생들이 자주 묻는 의문 — "그러면 $R^3, R^4$ 도 가능한가요?"

답 — 그렇다. 재귀적으로 정의 가능.

```
def RPow {A : Type} (R : A → A → Prop) : Nat → A → A → Prop
  | 0 => fun a b => a = b
  | n+1 => Comp R (RPow R n)
```

곧 $R^0$ 은 항등관계, $R^{n+1}$ 은 $R \circ R^n$. 모든 자연수 n 에 대해 자동.

이런 재귀 정의가 Lean 4 의 유도형 (inductive type) 시스템의 강점. 자세한 건 따로 강의.

## 블록 10 — `Comp R R` 의 구성 예

```lean
example {A : Type}
    (R : A → A → Prop)
    (a b c : A)
    (hab : R a b)
    (hbc : R b c) :
    Comp R R a c := by
  -- 목표: ∃ m, R a m ∧ R m c
  -- 중간 정점으로 b 를 제시
  exact ⟨b, hab, hbc⟩
```

자, 합성 관계의 멤버쉽을 직접 증명. "두 단계의 화살표가 있으면 합성 관계의 한 쌍을 만들 수 있다" 라는 사실.

`example {A : Type}` — 암묵 인수로 A. 호출 시 자동 추론.

`(R : A → A → Prop)` — 관계 R 을 명시 인수.

`(a b c : A)` — 세 원소.

`(hab : R a b)` — 가설 hab. 이름이 의미를 담음. h + a + b — "a 와 b 사이의 가설".

`(hbc : R b c)` — 가설 hbc. b 와 c 사이의 가설.

이런 이름 짓기가 가독성 좋음. 다른 사람이 코드를 읽을 때 — `hab` 가 무엇인지 즉시 짐작 가능.

`: Comp R R a c` — 결론. "a 와 c 가 R 의 자기 합성 관계에 있다". 곧 길이 2 경로의 한 쌍.

`:= by` — 전술 모드. 그러나 사실은 한 줄로 끝남.

`exact ⟨b, hab, hbc⟩` — 증명의 전부.

`exact` — 영어 단어 그대로 "정확히". 한국어 "정확". 진술 — "정확히 이 항이 목표의 증명임을 제공".

`⟨b, hab, hbc⟩` — 꺽쇠 표기. 우리가 블록 5 에서 본 그 꺽쇠. 그러나 이번에는 분해가 아니라 묶음.

자, 분석. 목표 `Comp R R a c` 를 정의대로 펼치면 — `∃ m, R a m ∧ R m c`. 

증명을 위해 필요한 것 — (1) 어떤 m 인지 증인 (witness) 제시, (2) `R a m` 의 증명, (3) `R m c` 의 증명.

꺽쇠 `⟨b, hab, hbc⟩` 가 세 부분.

`b` — 증인. m 자리에 b 를 제시. "중간 정점이 b 이다" 라는 선언.

`hab` — `R a b` 의 증명. 가설 hab 가 정확히 이 형태.

`hbc` — `R b c` 의 증명. 가설 hbc.

그러면 우리가 증명한 것 — "중간 정점 m = b 가 존재하고, 그 b 에 대해 R a b 와 R b c 가 모두 성립" → "Comp R R a c 가 성립".

이게 존재 증명의 표준 패턴 — 증인을 직접 제시. 구성적 증명 (constructive proof) 이라 부름. 영어 "constructive", 한국어 "구성적". 진술 — "존재 명제를 증명할 때 그 객체를 실제로 만들어 제시한다".

InfoView 변화 — 전 — 목표 `Comp R R a c`. 후 — `No goals`. 한 줄로 끝.

학생들이 자주 묻는 의문 — "꺽쇠 안에 세 가지가 있는데, 정확히 어떻게 작동하나요?"

답 — 자동 평탄화 (automatic flattening). `⟨b, hab, hbc⟩` 가 사실 `⟨b, ⟨hab, hbc⟩⟩` 의 줄임.

분해. 바깥 꺽쇠 `⟨b, ⟨hab, hbc⟩⟩` — 존재 명제의 증명. 두 부분 (증인 + 본체). 안쪽 꺽쇠 `⟨hab, hbc⟩` — 합접의 증명. 두 부분.

곧 외층이 ∃ 의 증명, 내층이 ∧ 의 증명. 두 꺽쇠가 중첩. Lean 4 가 평탄화해서 한 꺽쇠로 적을 수 있게 해 줌. 편의.

가설 `hab : R a b` 와 `hbc : R b c` 가 이미 `b` 라는 정점에 대해 주어짐. 증인이 가설에서 직접 제공. 

일반 증명에서는 증인을 직접 구성해야. 어려운 작업. 우리 예제는 가설이 친절해서 쉬움.

"왜 `exact` 인가? 다른 전술도 가능?"

 `refine ⟨b, hab, hbc⟩` 도 가능. 차이 — `exact` 는 완전 일치 요구, `refine` 는 부분적 미완성 허용 (?_ 같은 placeholder 가능). 우리 경우는 완전하므로 exact.

또는 — 꺽쇠 없이 명시적 함수 호출. `Exists.intro b (And.intro hab hbc)`. 정확히 같은 의미지만 길다. 꺽쇠가 가독성과 간결성 좋음.

수학적 의미 — "$a \to b$ 화살표와 $b \to c$ 화살표가 있으면, $a \to c$ 의 길이 2 경로가 존재" 라는 자연스러운 사실. 종이에 한 줄로 적을 그 사실이 Lean 4 의 한 줄 코드.

## 블록 11 — 합성의 결합법칙

```lean
example {A : Type} (R S T : A → A → Prop) (a d : A) :
    Comp (Comp R S) T a d ↔ Comp R (Comp S T) a d := by
  constructor
  · rintro ⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩
    -- 왼쪽 묶음을 풀면 b, c 라는 두 중간 정점이 나온다
    exact ⟨b, hRab, c, hSbc, hTcd⟩
  · rintro ⟨b, hRab, c, hSbc, hTcd⟩
    -- 오른쪽 묶음을 풀어 같은 b, c 로 왼쪽을 구성
    exact ⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩
```

자, 가장 큰 정리. 합성의 결합법칙 (associativity). $(T \circ S) \circ R = T \circ (S \circ R)$. 

`example {A : Type} (R S T : A → A → Prop) (a d : A)` — 세 관계 R, S, T 와 두 정점 a, d.

`: Comp (Comp R S) T a d ↔ Comp R (Comp S T) a d` — 결론.

`Comp (Comp R S) T a d` — `R ∘ S` 를 먼저 하고 `T` 를 다음에. 곧 (R 와 S 합성) 과 T 의 합성.

`Comp R (Comp S T) a d` — R 을 먼저 하고 `S ∘ T` 다음에. 곧 R 과 (S 와 T 합성) 의 합성.

`↔` — 둘이 동치. 양방향.

수학으로 — "어떤 순서로 묶어 합성하든 결과 동일." 결합법칙.

`:= by constructor` —

`constructor` — 블록 5 에서 본 그 전술. 결론이 `↔` 형태일 때 두 부 목표로 분해. 양방향을 따로.

InfoView 변화 — 전 — 목표 `Comp (Comp R S) T a d ↔ Comp R (Comp S T) a d`. 후 — 두 부 목표. (1) 왼쪽 → 오른쪽 방향. (2) 오른쪽 → 왼쪽 방향.

자, 첫 부 목표.

`· rintro ⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩` —

`·` — 부 목표 시작.

`rintro` — 새 전술. recursive intro 의 줄임.

`intro` — 영어 단어 그대로 "도입". 한국어 "도입". 진술 — "가정을 받아 자유 변수로 둠".

`rintro` — `intro` 의 강화판. 가정을 받으면서 동시에 패턴 매칭으로 분해.

`⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩` — 중첩 꺽쇠. 가정의 구조를 그대로 풀어 적음.

자, 분석. 첫 부 목표의 가정이 무엇인가. `Comp (Comp R S) T a d`. 정의를 펼치면 — `∃ c, (Comp R S) a c ∧ T c d`. 여기 `Comp R S` 를 또 펼치면 — `∃ c, (∃ b, R a b ∧ S b c) ∧ T c d`.

곧 — 중간 정점 c 존재, 그 c 에 대해 더 중간 정점 b 존재, `R a b`, `S b c`, `T c d` 모두 성립.

꺽쇠 `⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩` 가 이 구조 그대로 분해.

`c` — 외층 ∃ 의 증인.

`⟨b, hRab, hSbc⟩` — 외층 ∧ 의 왼쪽 부분. 내층 ∃ ∧.

  - `b` — 내층 ∃ 의 증인.
  - `hRab` — `R a b` 의 증명.
  - `hSbc` — `S b c` 의 증명.

`hTcd` — 외층 ∧ 의 오른쪽 부분. `T c d` 의 증명.

InfoView 변화 — 전 — 가정 `(Comp (Comp R S) T a d)`. 후 — `c, b : A`, `hRab : R a b`, `hSbc : S b c`, `hTcd : T c d` 모두 자유 변수와 가설로 도입.

`exact ⟨b, hRab, c, hSbc, hTcd⟩` — 결론을 구성.

목표 — `Comp R (Comp S T) a d`. 정의를 펼치면 — `∃ b, R a b ∧ (∃ c, S b c ∧ T c d)`.

꺽쇠 `⟨b, hRab, c, hSbc, hTcd⟩` 가 이 구조 그대로 구성.

`b` — 외층 ∃ 의 증인.

`hRab` — 외층 ∧ 의 왼쪽. R a b 의 증명.

`c` — 내층 ∃ 의 증인.

`hSbc` — 내층 ∧ 의 왼쪽. S b c 의 증명.

`hTcd` — 내층 ∧ 의 오른쪽. T c d 의 증명.

곧 — 왼쪽 표현에서 얻은 정보를 그대로 오른쪽 형식으로 재배열. 내용은 같고 묶는 방식만 다름.

`· rintro ⟨b, hRab, c, hSbc, hTcd⟩` 와 `exact ⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩` — 둘째 부 목표.

같은 일을 반대 방향. 오른쪽 표현 분해, 왼쪽 형식으로 재구성. 거의 복사·붙여넣기 수준의 대칭성.

자, 결합법칙의 의미 — "같은 중간 정점들을 다르게 묶은 것뿐". 왼쪽도 오른쪽도 결국 같은 b, c 두 중간 정점 사용. 묶는 방식만 다름.

학생들이 자주 묻는 의문 — "함수 합성의 결합법칙은 자명한 줄 알았는데, Lean 증명이 이렇게 긴 이유는?"

답 — 수학에서 자명한 사실도 Lean 4 에서는 정확한 단계가 필요. 왼쪽 형식과 오른쪽 형식이 글자 그대로 같지 않으므로 꺽쇠 분해와 재조립이 명시. 형식 증명의 본성.

다만 Mathlib 에는 결합법칙이 이미 증명되어 있어 실전에서는 한 줄 호출. 우리는 원리 이해를 위해 직접 증명. 교육용.

또 의문 — "`rintro` 와 `intro + obtain` 의 차이는?"

답 — 기능은 같지만 표기가 압축적. `rintro ⟨c, ⟨b, hRab, hSbc⟩, hTcd⟩` 가 `intro h; obtain ⟨c, hc⟩ := h; ...` 같은 여러 줄을 한 줄로. 길이는 1/4.

## 블록 12 — 다섯 가지 관계 성질의 정의

```lean
variable {A : Type}

def Refl  (R : A → A → Prop) : Prop := ∀ a, R a a
def Symm  (R : A → A → Prop) : Prop := ∀ a b, R a b → R b a
def Trans1 (R : A → A → Prop) : Prop :=
  ∀ a b c, R a b → R b c → R a c
def Antisymm (R : A → A → Prop) : Prop :=
  ∀ a b, R a b → R b a → a = b

-- 동치관계: 세 성질을 ∧ 로 묶는다
def Equiv1 (R : A → A → Prop) : Prop :=
  Refl R ∧ Symm R ∧ Trans1 R
```

자, 이번이 relation 5.4 절의 핵심. 다섯 가지 성질을 Lean 4 로.

먼저 첫 줄 `variable {A : Type}`.

`variable` — 영어 단어 그대로 "변수". 한국어 "변수". 진술 — "이 파일에서 다음 정의들에 자동으로 추가될 인수를 선언".

`{A : Type}` — 암묵 인수 A 를 선언. 

`variable {A : Type}` 의 의미 — "이 줄 이후 모든 def 와 example 에서 `{A : Type}` 가 자동으로 추가된다". 곧 우리가 매번 `{A : Type}` 를 적지 않아도 됨.


###"variable 이 정확히 어디까지 적용되나요?"

같은 namespace 또는 section 안의 후속 정의들. 우리 파일에서는 그 뒤의 모든 def 와 example. 명시적으로 끝내려면 `section` 과 `end` 같은 블록을 따로 두는데 우리 코드는 단순히 파일 전체에 적용.

자, 이제 다섯 정의를 차례로.

### Refl — 반사성

`def Refl (R : A → A → Prop) : Prop := ∀ a, R a a`

`Refl` — Reflexive (반사적) 의 줄임.

`(R : A → A → Prop)` — 관계 R 을 명시 인수.

`: Prop` — 반환 타입. 명제. 곧 "Refl R" 자체가 명제. "R 이 반사관계이다" 라는 주장.

`:= ∀ a, R a a` — 본체.

`∀` — 새 기호. 전체 양화사 (universal quantifier). 영어 "for all", 한국어 "모든". 키보드 `\forall` 또는 `\all`. 진술 — "모든 a 에 대해 그 다음 조건이 성립".

수학의 $\forall$ 와 같음. 자주 보는 그 기호.

`∀ a, R a a` — "모든 a 에 대해 R a a 가 성립". 곧 모든 원소가 자기 자신과 R 관계.

수학적 정의 — $R$ 이 반사관계 ⇔ $\forall a, (a, a) \in R$. Lean 4 표현과 1:1 대응.

### Symm — 대칭성

`def Symm (R : A → A → Prop) : Prop := ∀ a b, R a b → R b a`

`Symm` — Symmetric (대칭적).

`∀ a b, R a b → R b a` — "모든 a, b 에 대해 R a b 이면 R b a".

`∀ a b,` — 변수 두 개의 양화. `∀ a, ∀ b,` 의 줄임.

`→` — 함수 화살표인데 여기서는 함의 (implication) 의 의미. "~이면 ~".

자, 함수 타입의 `→` 와 함의의 `→` 가 같은 기호. 우연이 아니라 두 개념이 본질적으로 같음. "P 이면 Q" 는 "P 의 증명을 Q 의 증명으로 변환하는 함수". 깊은 논리학 사실.

수학적 정의 — $R$ 이 대칭관계 ⇔ $\forall a, b, (a, b) \in R \to (b, a) \in R$. 1:1 대응.

### Trans1 — 추이성

`def Trans1 (R : A → A → Prop) : Prop := ∀ a b c, R a b → R b c → R a c`

`Trans1` — Transitive (추이적) 의 일종. 1 이 붙은 이유 — Mathlib 의 `Transitive` 와 이름이 충돌하지 않게. 우리 정의는 학습용 사본.

`∀ a b c, R a b → R b c → R a c` — 세 변수와 두 함의.

`R a b → R b c → R a c` — "R a b 이면 (R b c 이면 R a c)" 의 의미. 함의가 연속.

자, 함의 화살표가 두 번 연속. Lean 4 의 `→` 는 오른쪽 결합. 곧 `A → B → C` 가 `A → (B → C)`. 곧 "A 이면 (B 이면 C)". 

곧 "R a b 와 R b c 가 둘 다 주어지면 R a c". 추이성 정확히.

학생들이 자주 묻는 의문 — "왜 함의 두 개고 합접 (∧) 한 개가 아닌가요?"

답 — 둘 다 가능. `R a b ∧ R b c → R a c` 와 `R a b → R b c → R a c` 가 논리적으로 동등. 다만 후자가 부분 적용에 편리. "R a b 만 받아 (R b c → R a c) 라는 함수를 돌려줌". 두 단계 적용 가능.

### Antisymm — 반대칭성

`def Antisymm (R : A → A → Prop) : Prop := ∀ a b, R a b → R b a → a = b`

`Antisymm` — Antisymmetric (반대칭적).

`∀ a b, R a b → R b a → a = b` — "모든 a, b 에 대해, R a b 이고 R b a 이면 a = b".

곧 양방향 관계가 있으면 같은 원소여야. 7 장의 부분순서관계의 핵심 성질.

`a = b` — 결론이 등식. Prop 타입.

### Equiv1 — 동치관계

`def Equiv1 (R : A → A → Prop) : Prop := Refl R ∧ Symm R ∧ Trans1 R`

`Equiv1` — Equivalence (동치).

`Refl R ∧ Symm R ∧ Trans1 R` — 세 성질의 합접. 동치관계의 정의.

자, 합접이 두 번 연속. `A ∧ B ∧ C` 가 `A ∧ (B ∧ C)` 로 오른쪽 결합. 슬라이드 17 의 증명에서 두 번 분해해야 하는 이유.

수학적 정의 — $R$ 이 동치관계 ⇔ R 이 반사 ∧ 대칭 ∧ 추이. relation 5.4 절의 봉우리.

학생들이 자주 묻는 의문 — "다섯 가지 성질이라 했는데 정의는 네 개 + 동치관계 = 다섯 인가요? 비반사, 비대칭은?"

답 — 우리 코드는 다섯 중 네 가지만 정의. 비반사, 비대칭은 부정 (¬) 을 써서 정의 가능. 

`def Irrefl (R : A → A → Prop) : Prop := ∀ a, ¬ R a a` — 비반사.
`def Asymm (R : A → A → Prop) : Prop := ∀ a b, R a b → ¬ R b a` — 비대칭.

`¬` — 부정. 블록 19 에서 자세히. 

또 의문 — "Mathlib 에 이미 같은 정의가 있나요?"

그렇다. `Reflexive`, `Symmetric`, `Transitive`, `Equivalence` 가 Mathlib 표준 이름. 우리 정의는 학습용 변종. 실전에서는 Mathlib 사용.

## 블록 13 — `Le` 가 반사관계임을 증명

```lean
def Le1 : Nat → Nat → Prop :=
  fun a b => a ≤ b

-- Le 는 반사관계
example : Refl Le := by
  -- 목표: ∀ a, Le a a
  intro a
  show a ≤ a
  omega
```

자, 첫 형식 증명. `Le` 가 반사관계임.

먼저 `def Le1` — 블록 6 의 `Le` 와 같은 정의이지만 이름이 `Le1`. 이유 — Mathlib 의 다른 정의와의 충돌 회피, 그리고 후속 `unfold` 명령에서의 안전한 펼침. 학습용 의도된 중복.

`example : Refl Le := by` — "Le 가 반사관계임을 증명한다." 

자, 결론 `Refl Le` 가 명제. `Refl` 정의를 펼치면 — `∀ a, Le a a`. 곧 모든 자연수 a 에 대해 `Le a a` 가 성립.

`:= by intro a` —

`intro` — 새 전술. 영어 "introduce", 한국어 "도입". 진술 — "전체 양화사 ∀ 또는 함의 → 를 푸는 전술".

`∀ a, P a` 형태의 목표에 `intro a` 를 적용하면 — "임의의 a 를 잡고, 그 a 에 대해 P a 를 보이겠다" 로 변환. 수학에서 "임의의 a 를 잡는다" 와 정확히 같음.

InfoView 변화 — 전 — 목표 `∀ a, Le a a`. 후 — 자유 변수 `a : Nat`, 목표 `Le a a`. 양화사가 사라지고 자유 변수가 등장.

`show a ≤ a` — 목표 명시.

`Le a a` 의 정의 펼침 — `(fun a b => a ≤ b) a a` 가 평가되어 `a ≤ a`. 곧 `Le a a` 가 정의상 `a ≤ a`. show 가 두 형태의 동등성을 명시.

InfoView 변화 — 전 — 목표 `Le a a`. 후 — 목표 `a ≤ a`. 시각적 명확.

`omega` — 우리가 익숙한 그 전술. `a ≤ a` 가 모든 자연수에 자명. omega 가 즉시 닫음.

자, 수학과 Lean 4 의 1:1 대응.

| 수학 | Lean 4 |
|---|---|
| "임의의 a 를 잡고" | `intro a` |
| "Le 의 정의에 의해 a ≤ a" | `show a ≤ a` |
| "a ≤ a 자명" | `omega` |

세 줄로 끝. 형식 증명의 매끄러움.

 — "`show` 가 꼭 필요한가요?"

 — 생략 가능. omega 가 자동으로 정의 펼침. 우리 코드는 학습용 명시성. 실전에서는 `intro a; omega` 두 줄이면 충분.

 — "왜 a 가 두 번 등장하는데 intro 가 한 번만?"

 — `∀ a, R a a` 가 한 변수 a 에 대한 양화. R a a 안에서 a 가 두 번 나타나지만 한 변수의 두 번 사용. 그래서 intro a 한 번이면 충분.

 — "intro 의 자유 변수가 정확히 무엇인가요?"

 — `intro a` 후 a 가 임의의 자연수를 나타내는 자유 변수. "어떤 특정 a 도 아니고 모든 a 를 대표하는 a". 수학적으로 같은 의미.

## 블록 14 — `EqR` 가 대칭관계임을 증명

```lean
def EqR (A : Type) :
    A → A → Prop :=
  fun a b => a = b


example {A : Type} :
    Symm (EqR A) := by
  -- ∀ a b, a=b → b=a
  intro a b h
  show b = a
  exact h.symm
```


###`EqR` 정의부터. 영어 "Equality Relation"임. 등호 관계를 명시적 함수로.

`def EqR (A : Type) : A → A → Prop := fun a b => a = b` — 

타입 매개변수 A 를 명시 인수로. 두 인수 a, b 를 받아 `a = b` 명제 반환.

수학에서 등호 = 자체가 한 관계. 그걸 함수로 명시적 표현.

`example {A : Type} : Symm (EqR A) := by`

`{A : Type}` — 암묵 인수. (앞서 `variable {A : Type}` 가 있어 사실 생략 가능하지만 명시.)

`Symm (EqR A)` — "EqR 이 대칭관계이다" 라는 명제. `Symm` 정의 펼침 — `∀ a b, R a b → R b a`. R 자리에 EqR A.

`intro a b h` — 

`intro` 가 세 가지를 동시에 받음. 

`∀ a b, R a b → R b a` 의 구조 — (1) ∀ a, (2) ∀ b, (3) 함의의 가설 R a b.

`intro a b h` 가 세 단계를 한 줄에. a, b, 그리고 함의 가설 h 를 차례로 받음. 짧고 효율적.

`intro` 가 한 번에 여러 개 받을 수 있는 게 Lean 4 의 편의. `intro a; intro b; intro h` 세 줄과 동등.

InfoView 변화 — 전 — 목표 `∀ a b, EqR A a b → EqR A b a`. 후 — `a b : A`, `h : EqR A a b` (정의 펼침으로 `h : a = b`), 목표 `EqR A b a` (= `b = a`).

`show b = a` — 목표 명시.

`exact h.symm` — 새 전술 사용.

`h.symm` — 점 표기. `h` 의 점 다음 `symm` 메서드.

`symm` — Symmetric (대칭) 의 줄임. 등호 또는 동치관계의 대칭성을 적용하는 함수.

`h : a = b` 가 있을 때, `h.symm` 은 `b = a` 의 증명. 곧 `Eq.symm h` 의 단축 표기.

자, 점 표기가 어떻게 작동하는가. `h` 의 타입이 `Eq` (등식). Lean 4 가 `Eq` 타입의 메서드 `symm` 을 찾아 자동 적용. `h.symm` = `Eq.symm h`.

이런 점 표기가 Lean 4 의 매우 자주 쓰는 도구. 가독성 좋음. 

`exact h.symm` — "정확히 h.symm 이 우리 목표 b = a 의 증명이다". exact 가 매칭 확인. 통과.

InfoView 변화 — 전 — 목표 `b = a`. 후 — No goals.

자, 수학과 Lean 4 의 대응.

| 수학 | Lean 4 |
|---|---|
| "임의의 a, b 잡고" | `intro a b` |
| "a = b 가정" | `intro h` |
| "등호 대칭으로 b = a" | `exact h.symm` |

수학 추론 3 단계가 코드 3 줄.

학생들이 자주 묻는 의문 — "`h.symm` 대신 다른 방법은?"

답 — 여러 가지 가능.

`rw [h]` — h 의 좌우를 사용해 목표의 a 를 b 로 치환. 목표 `b = a` 가 `b = b` 가 되고 자동 닫힘.

`exact Eq.symm h` — h.symm 의 풀이 형태.

`symm` — 그냥 전술. 목표가 등식이면 좌우 교환. 그 다음 `exact h`.

세 방식 모두 같은 결과. 점 표기가 가장 짧고 우아함. 

또 의문 — "h.symm 같은 점 표기가 어떻게 자동 작동하나요?"

답 — Lean 4 의 dot notation 자동 해석. `h.foo` 가 있으면 Lean 4 가 h 의 타입 T 를 보고 `T.foo h` 또는 적절한 변환을 시도. 우리 경우 `h : a = b` 의 타입이 `Eq a b`, 따라서 `Eq.symm h` 호출. 매우 편리.

## 블록 15 — `Le1` 가 추이관계임을 증명

```lean
example : Trans1 Le1 := by
  -- ∀ a b c, Le1 a b → Le1 b c → Le1 a c
  intro a b c hab hbc
  -- hab : Le1 a b
  -- hbc : Le1 b c
  unfold Le1 at hab hbc
  -- 이제 hab : a ≤ b, hbc : b ≤ c
  show a ≤ c
  omega
```

자, 추이성 증명. `Le1` 이 추이관계.

`Trans1` 정의 펼침 — `∀ a b c, R a b → R b c → R a c`. 곧 세 변수와 두 함의.

`intro a b c hab hbc` — 다섯 가지를 한 줄에 받음.

세 변수 a, b, c — 양화사 세 번. 두 가설 hab, hbc — 함의 두 번.

가설 이름이 의미를 가짐. `hab` = "a 와 b 사이의 가설", `hbc` = "b 와 c 사이의 가설". 가독성.

InfoView 변화 — 후 — `a b c : Nat`, `hab : Le1 a b`, `hbc : Le1 b c`, 목표 `Le1 a c`.

`unfold Le1 at hab hbc` — 새 전술.

`unfold` — 영어 단어 "펴다, 펼치다". 한국어 "펼침". 진술 — "정의를 강제로 펼친다".

`unfold Le1` — Le1 의 정의를 펼침. `Le1 := fun a b => a ≤ b`. 펼친 결과 — `a ≤ b`.

`at hab hbc` — 두 가설에 동시 적용. 우리가 블록 5 에서 본 `at h` 의 확장.

InfoView 변화 — 전 — `hab : Le1 a b`, `hbc : Le1 b c`. 후 — `hab : a ≤ b`, `hbc : b ≤ c`. 정의가 펼쳐져 순수 부등식.

자, 왜 `unfold` 가 필요한가. 목표는 `Le1 a c` 인데 우리가 `show a ≤ c` 로 명시할 예정. 그러나 가설 hab, hbc 도 omega 가 처리하려면 `a ≤ b`, `b ≤ c` 같은 순수 부등식이어야 함. unfold 가 가설들을 그 형태로.

`show a ≤ c` — 목표를 부등식으로 명시.

`omega` — 두 부등식 가설과 목표를 종합. `a ≤ b ∧ b ≤ c → a ≤ c` — 부등식의 추이성. omega 가 자동 도출.

학생들이 자주 묻는 의문 — "show 와 unfold 의 차이는?"

답 — 비슷하지만 위치가 다름. `show` 는 목표만, `unfold` 는 목표·가설 모두 가능. 또 `show` 는 동등한 다른 형태를 명시, `unfold` 는 특정 정의를 펼침. 둘 다 정의 등치를 활용.

또 의문 — "omega 가 두 부등식을 어떻게 결합하나요?"

답 — 선형 산술의 결정 알고리즘. 가설 `a ≤ b` 와 `b ≤ c` 를 행렬 형태로 정규화 후 변수 b 를 소거. 결과 `a ≤ c`. 우리 목표와 일치. 0.001 초.

자, 수학과 코드의 대응.

| 수학 | Lean 4 |
|---|---|
| "임의의 a, b, c 잡고" | `intro a b c` |
| "a ≤ b 와 b ≤ c 가정" | `intro hab hbc` |
| "Le1 의 정의 펼치면 부등식" | `unfold Le1 at hab hbc` |
| "보일 것은 a ≤ c" | `show a ≤ c` |
| "부등식 추이성으로 a ≤ c" | `omega` |

수학 5 단계가 코드 5 줄.

## 블록 16 — `EqR` 가 동치관계임을 증명

```lean
example {A : Type} : Equiv1 (EqR A) := by
  -- 목표: Refl (EqR A) ∧ Symm (EqR A) ∧ Trans1 (EqR A)
  constructor
  · intro a
    show a = a
    rfl
  · constructor
    · intro a b h
      show b = a
      exact h.symm
    · intro a b c hab hbc
      show a = c
      exact Eq.trans hab hbc
```

자, relation 5.4 절의 봉우리. 등호가 동치관계임을 증명. 세 성질을 한꺼번에.

`Equiv1 (EqR A)` 의 정의 펼침 — `Refl (EqR A) ∧ Symm (EqR A) ∧ Trans1 (EqR A)`. 세 성질의 합접. 

합접이 두 번 연속이라 — `A ∧ B ∧ C` 가 `A ∧ (B ∧ C)`. constructor 가 두 번 필요.

`constructor` — 첫 합접 분해.

InfoView 변화 — 전 — 목표 `Refl (EqR A) ∧ Symm (EqR A) ∧ Trans1 (EqR A)`. 후 — 두 부 목표. (1) `Refl (EqR A)`, (2) `Symm (EqR A) ∧ Trans1 (EqR A)`.

자, 첫 부 목표 (반사성).

`· intro a; show a = a; rfl` — 

`intro a` — 임의의 a 잡음. ∀ a, ... 분해.

`show a = a` — 목표를 등식으로. EqR A a a 가 정의상 a = a.

`rfl` — 자명. 닫힘.

두 번째 부 목표 — `Symm (EqR A) ∧ Trans1 (EqR A)`. 또 합접.

`· constructor` — 두 번째 합접 분해.

InfoView 변화 — 후 — 두 새 부 목표. (1) `Symm (EqR A)`, (2) `Trans1 (EqR A)`.

대칭성 부 목표 — 블록 14 의 패턴 그대로.

`· intro a b h; show b = a; exact h.symm`.

추이성 부 목표 — 새로운 모습.

`· intro a b c hab hbc` — 세 변수와 두 가설.

`show a = c` — 목표 명시. `EqR A a c` 가 `a = c`.

`exact Eq.trans hab hbc` — 새 도구.

`Eq.trans` — 등호의 추이성 정리. Mathlib 의 표준 정리. 시그너처 — `Eq.trans : a = b → b = c → a = c`.

`Eq.trans hab hbc` — hab 와 hbc 를 차례로 적용해 `a = c` 도출. 

자, 이게 함수 호출 형태의 증명. `Eq.trans` 라는 정리가 사실 함수 — 두 등식 가설을 받아 새 등식을 돌려주는 함수. 우리가 hab, hbc 를 인수로 적용.

exact 가 결과를 우리 목표와 매칭. 통과.

학생들이 자주 묻는 의문 — "h.symm 같은 점 표기는 안 쓰나요?"

답 — 가능. `hab.trans hbc` 같이 점 표기로도 적을 수 있어요. 같은 의미. 우리 코드는 명시적 함수 호출을 사용해 학생이 어떤 정리를 호출하는지 분명하게.

또 의문 — "constructor 두 번 쓰는 게 좀 어색해요."

답 — 대안 가능. `refine ⟨?_, ?_, ?_⟩` 처럼 세 부 목표를 한 번에 만들거나, term 모드로 `⟨반사_증명, 대칭_증명, 추이_증명⟩` 직접 적기. 다양한 방식. 우리 코드는 단계적·교육적.

수학적 의미 — 등호가 동치관계의 가장 단순한 예. 세 성질 (반사, 대칭, 추이) 모두 자명하게 만족.

자, 블록 전체의 큰 그림. `Equiv1 (EqR A)` 라는 한 명제를 증명하는데 — 세 성질을 차례로 증명. 각 부 증명이 작은 example. 합쳐서 큰 정리. 모듈식 증명의 좋은 예.

## 블록 17 — `Le` 가 반대칭관계임을 증명

```lean
example : Antisymm Le := by
  -- 목표: ∀ a b, Le a b → Le b a → a = b
  intro a b hab hba
  -- hab : a ≤ b, hba : b ≤ a 가 되도록 Le 의 정의를 펼친다
  unfold Le at hab hba
  show a = b
  omega
```

자, 반대칭성. 7 장의 부분순서관계의 토대.

`Antisymm` 정의 펼침 — `∀ a b, R a b → R b a → a = b`. 양방향이면 같은 원소.

`intro a b hab hba` — 두 변수와 두 가설을 한 줄에.

가설 이름 — `hab` (a 와 b 사이의 R), `hba` (b 와 a 사이의 R). 

`unfold Le at hab hba` — 두 가설에서 Le 정의를 펼침. `Le a b` → `a ≤ b`, `Le b a` → `b ≤ a`.

`show a = b` — 목표 명시.

`omega` — 두 부등식 가설 `a ≤ b` 와 `b ≤ a` 가 동시에 성립하면 `a = b`. 부등식의 반대칭성 (자연수, 정수의 기본 사실). omega 자동 처리.

자, 반대칭성과 비대칭성의 차이 한 번 짚어요.

반대칭 (Antisymm) — `R a b ∧ R b a → a = b`. 양방향이면 같은 원소. 대각선 (a = b) 허용.

비대칭 (Asymm) — `R a b → ¬ R b a`. 한 방향이면 다른 방향 없음. 대각선 금지.

`Le` (≤) — 반대칭이지만 비대칭은 아님. `1 ≤ 1` 이 양방향이라도 (자기 자신) `a = a` 라 반대칭 조건 만족. 그러나 비대칭은 `1 ≤ 1 → ¬ 1 ≤ 1` 인데 모순.

`<` (실제 작음) — 비대칭. 대각선이 없음. 둘 다 만족.

비대칭 ⇒ 반대칭. 역은 성립 안 함.

학생들이 자주 묻는 의문 — "omega 가 정말 반대칭성을 안다고요?"

답 — omega 가 결정 알고리즘. `a ≤ b ∧ b ≤ a` 같은 가설들에서 `a = b` 같은 결론을 자동 도출. 산술적 보조정리들이 알고리즘 안에 내장. 학생이 신경 쓸 필요 없음.

자, 수학과 코드 대응.

| 수학 | Lean 4 |
|---|---|
| "a ≤ b 와 b ≤ a 가정" | `intro a b hab hba` + `unfold Le` |
| "보일 것은 a = b" | `show a = b` |
| "두 부등식 결합해 등식" | `omega` |

수학 한 줄 추론이 코드 한 전술.

## 블록 18 — 역관계 `Inv1` 과 여관계 `Compl1` 정의

```lean
variable {A : Type}

-- 역관계: a 와 b 의 자리를 바꾼다
def Inv1 (R : A → A → Prop) : A → A → Prop :=
  fun a b => R b a

-- 여관계: 관계의 부정
def Compl1 (R : A → A → Prop) : A → A → Prop :=
  fun a b => ¬ R a b
```

자, 5.5 절의 두 연산을 Lean 4 로.

`variable {A : Type}` — 다시 변수 선언. 후속 정의들에서 A 자동.

### Inv1 — 역관계

`def Inv1 (R : A → A → Prop) : A → A → Prop := fun a b => R b a`

`Inv1` — Inverse (역) 의 줄임.

함수 본체 `fun a b => R b a` — 두 인수 a, b 를 받아 `R b a` 명제 반환.

주목할 점 — 인수 순서가 바뀜. 호출 `Inv1 R a b` 가 내부에서 `R b a`. 곧 a 와 b 의 자리를 뒤집어서 R 에 넘김.

수학에서 — $R^{-1} = \{(b, a) \mid (a, b) \in R\}$. 곧 모든 순서쌍의 자리 변경. Lean 4 의 `fun a b => R b a` 와 정확히 같음.

비유 — 친구 관계가 "내가 그를 친구로 둠" 이라면 역관계는 "그가 나를 친구로 둠". 같은 관계의 반대 관점.

### Compl1 — 여관계

`def Compl1 (R : A → A → Prop) : A → A → Prop := fun a b => ¬ R a b`

`Compl1` — Complement (여, 보완) 의 줄임.

함수 본체 `fun a b => ¬ R a b` — `R a b` 의 부정.

`¬` — 새 기호. 부정 (negation). 영어 "not", 한국어 "아니다". 키보드 `\not` 또는 `\neg`. 진술 — "다음 명제의 부정".

`¬ R a b` 의 의미 — "R a b 가 거짓" 또는 "(a, b) 가 R 에 없음".

내부 동작 — Lean 4 에서 `¬ P` 는 `P → False` 의 정의 등치. 곧 "P 라면 모순". 부정의 우아한 표현.

수학에서 — $\overline{R} = (A \times A) \setminus R = \{(a, b) \mid (a, b) \notin R\}$. R 의 바깥. Lean 4 의 `fun a b => ¬ R a b` 와 같음.

자, 두 정의의 공통점과 차이점.

공통 — 둘 다 R 로부터 새 관계를 만드는 함수. 둘 다 `A → A → Prop` 반환.

차이 — Inv1 은 인수 순서 변경, Compl1 은 부정.

학생들이 자주 헷갈리는 함정. 이름이 비슷하지만 하는 일이 완전히 다름. 한 번 더 강조 — Inv 가 방향 뒤집기, Compl 이 멤버쉽 반전.

학생들이 자주 묻는 의문 — "그러면 Inv 와 Compl 이 같을 수도 있나요?"

답 — 일반적으로 다름. 예외적 작위적 관계만이 같음. 자연 관계에서는 서로 다른 결과.

또 의문 — "역관계와 여관계 외에 다른 관계 연산은?"

답 — 합집합 `R ∪ S`, 교집합 `R ∩ S`, 차 `R \ S` 등 집합 연산을 관계에 적용 가능. 또 합성 (Comp). 우리 코드는 가장 기본적인 두 가지만.

또 한 가지 — `¬ P` 의 정확한 의미.

답 — `¬ P` = `P → False`. 곧 "P 가 참이라고 가정하면 모순 (False) 이 따라옴". 거짓의 정의. 

자, 이게 깊은 논리학 주제. 직관 — "P 가 거짓" 이라는 것을 어떻게 증명? "P 가 참이라고 해 봐, 그러면 모순이지" 라는 논증. 일상적인 귀류법의 형식적 표현.

## 블록 19 — 역관계의 역관계는 자기 자신

```lean
example (R : A → A → Prop)
    (a b : A) :
    Inv1 (Inv1 R) a b ↔ R a b := by
  -- Inv1 (Inv1 R) a b
  --   = Inv1 R b a
  --   = R a b
  rfl
```

자, 짧지만 매우 인상적인 증명.

`Inv1 (Inv1 R) a b` — 역관계의 역관계를 a, b 에 적용. 풀어 보자.

`Inv1 (Inv1 R)` — Inv1 함수를 Inv1 R 에 적용. 결과는 새 관계.

`Inv1 (Inv1 R) a b` — 그 새 관계를 a, b 에 적용.

자, 정의를 두 번 펼치면 어떻게 되는가.

`Inv1 R` = `fun a b => R b a`. 곧 인수를 뒤집어 R 에 넘기는 함수.

`Inv1 (Inv1 R)` = `fun a b => (Inv1 R) b a`. 곧 인수를 뒤집어 Inv1 R 에 넘김.

`(Inv1 R) b a` = `Inv1 R` 에 b, a 적용. Inv1 R 정의 펼침 — `(fun x y => R y x) b a` = `R a b`.

종합 — `Inv1 (Inv1 R) a b` = `R a b`. 정의상 같음.

`:= by rfl` — 증명. 단 한 줄.

이게 정의 등치의 강력한 표현. 양변이 글자 그대로 같으니 rfl 한 줄로 닫힘.

수학적 의미 — "방향을 두 번 뒤집으면 원위치" 가 Lean 4 에서 "정의 두 번 펼치면 양변이 같음". 자명함의 정확한 형식적 표현.

학생들이 자주 묻는 의문 — "그러면 모든 자명한 사실이 rfl 로 닫히나요?"

답 — 정의상 동등한 사실만. 곧 양변이 계산만으로 글자 일치하는 경우. 정리를 호출해야 하는 사실은 안 됨.

예 — `R ∪ R = R` 같은 사실. 집합 합집합의 멱등성. Lean 4 에서는 정의 펼침만으로 안 됨. 정리 호출 (`Set.union_self` 같은) 필요. `rfl` 안 됨.

또 의문 — "그러면 이중 부정 `¬ ¬ P ↔ P` 도 rfl 로 닫히나요?"

답 — Lean 4 의 기본 논리에서는 안 됨. 직관주의 논리 (intuitionistic logic) 에서 `¬ ¬ P → P` 가 자동이 아님. 고전 논리 (classical logic) 의 추가 공리 필요. 우리 역관계는 단순 인수 변경이라 정의 등치로 충분.

자, 한 줄로 — 이 example 이 보여 주는 것 — "정의를 잘 만들면 핵심 정리가 자동으로 따라온다". 좋은 정의가 좋은 정리.

## 블록 20 — `R1`, `S1` 정의와 합성 예제

```lean
def R1 : Nat → Nat → Prop := fun a b => a = 1 ∧ b = 2
def S1 : Nat → Nat → Prop := fun a b => a = 2 ∧ b = 3

-- (1,3) 은 S∘R 에 있다: 중간 원소 2 를 거친다
example : Comp R1 S1 1 3 :=
  ⟨2, ⟨rfl, rfl⟩, ⟨rfl, rfl⟩⟩
```

자, 합성의 비가환성을 보이기 위한 구체적 예제. 두 단순한 관계.

`R1` 정의 — `fun a b => a = 1 ∧ b = 2`.

뜻 — "a = 1 이고 b = 2 인 두 자연수 쌍". 곧 관계 R1 은 단일 순서쌍 (1, 2) 만 포함. 단순한 관계.

`S1` 정의 — `fun a b => a = 2 ∧ b = 3`. 단일 순서쌍 (2, 3) 만 포함.

이렇게 단순하게 정의한 이유 — 합성을 추적하기 쉬워서. R1 ∘ S1 같은 결과가 손으로 명확히 보임.

`example : Comp R1 S1 1 3 := ⟨2, ⟨rfl, rfl⟩, ⟨rfl, rfl⟩⟩`

자, `Comp R1 S1 1 3` — R1 다음 S1 의 합성을 1, 3 에 적용. (1, 3) 이 합성 관계에 속하는지.

수학적으로 — R1 의 (1, 2) 다음 S1 의 (2, 3). 중간 원소 2 가 매개. 따라서 (1, 3) ∈ Comp R1 S1.

`:= ⟨2, ⟨rfl, rfl⟩, ⟨rfl, rfl⟩⟩` — 증명. term 모드.

이번엔 `by` 없이 직접 항을 적었어요. 짧은 증명에 적합한 방식.

꺽쇠 분석. 목표 `Comp R1 S1 1 3` 의 정의 펼침 — `∃ b, R1 1 b ∧ S1 b 3`.

꺽쇠 `⟨2, ⟨rfl, rfl⟩, ⟨rfl, rfl⟩⟩` 의 세 부분.

`2` — 증인. b 자리에 2. "중간 원소가 2 이다".

`⟨rfl, rfl⟩` — `R1 1 2` 의 증명. 

R1 1 2 의 정의 펼침 — `1 = 1 ∧ 2 = 2`. 합접 두 부분. 각각 자명. rfl 두 개로 닫음. 꺽쇠로 묶음.

`⟨rfl, rfl⟩` — `S1 2 3` 의 증명. 같은 방식. `2 = 2 ∧ 3 = 3`.

자, 총 네 개의 rfl 이 두 합접의 양쪽을 닫음. 모두 자명한 등식.

학생들이 자주 묻는 의문 — "왜 by 가 없나요?"

답 — 짧은 증명은 by 없이 term 모드가 더 깔끔. by 와 동등하지만 코드가 더 평탄. 우리 example 처럼 구조가 명확한 증명에 적합.

또 의문 — "꺽쇠가 자동으로 평탄화되는 거죠?"

답 — 그렇다. `⟨2, ⟨rfl, rfl⟩, ⟨rfl, rfl⟩⟩` 가 사실 `⟨2, ⟨⟨rfl, rfl⟩, ⟨rfl, rfl⟩⟩⟩` 의 줄임. 외층 ∃, 내층 ∧, 그 안에 두 합접의 ∧. 네 단계 중첩이 자동 평탄화.

자, 이 example 의 의미 — (1, 3) 이 R1 다음 S1 의 합성에 속함을 증명. 짧지만 합성의 멤버쉽 증명의 표준 패턴.

## 블록 21 — 합성의 비가환성을 반례로

```lean
-- (1,3) 은 R∘S 에는 없다
example : ¬ Comp S1 R1 1 3 := by
  rintro ⟨b, ⟨h1, h2⟩, h3⟩
  omega
```

자, 반대 방향의 합성. `Comp S1 R1` — S1 먼저, R1 다음. 합성의 순서를 바꿈.

수학적으로 — S1 의 (2, 3) 다음 R1 의 (1, 2)? S1 의 끝점 3 과 R1 의 시작점 1 이 일치하지 않음. 매칭 안 됨. 따라서 (1, 3) ∉ Comp S1 R1.

`¬ Comp S1 R1 1 3` — "(1, 3) 이 Comp S1 R1 에 속하지 않음" 이라는 부정 명제.

`:= by` — 전술 모드.

`rintro ⟨b, ⟨h1, h2⟩, h3⟩` — 부정 명제 증명의 핵심.

자, 부정 증명의 일반 패턴. `¬ P` 가 `P → False`. 곧 "P 를 가정하면 모순". 따라서 P 를 가정 (intro 또는 rintro) 하고 모순 도출.

여기 P = `Comp S1 R1 1 3` = `∃ b, S1 1 b ∧ R1 b 3`.

`rintro ⟨b, ⟨h1, h2⟩, h3⟩` 가 P 를 가정하면서 동시에 분해.

`b` — 증인.

`⟨h1, h2⟩` — `S1 1 b` 의 증명. S1 정의 펼침으로 `1 = 2 ∧ b = 3`. 두 부분.

  - `h1 : 1 = 2` — 첫 부분.
  - `h2 : b = 3` — 둘째 부분.

`h3` — `R1 b 3` 의 증명. R1 정의 펼침으로 `b = 1 ∧ 3 = 2`. 

자, 흠. 여기 코드의 rintro 패턴이 좀 단순한데 실제 가설은 더 복잡할 수 있음. 우리 코드는 핵심 모순을 빨리 찾기 위해 적당히 분해.

`h1 : 1 = 2` — 모순!

자, 이게 핵심. `1 = 2` 가 거짓. 자연수 1 과 2 가 다름이 자명. 그러나 가설로 들어와 있으면 — 모순. 모순 가정에서는 모든 명제가 따라옴 (ex falso quodlibet).

`omega` — 산술 모순을 자동 탐지. 가설에 `1 = 2` 같은 거짓 등식이 있으면 즉시 모순 처리. 결과 — `False` 도출. 그러면 우리가 증명해야 하는 어떤 목표든 자동 닫힘.

InfoView 변화 — 전 — `rintro` 후 가설들. 후 — `omega` 가 `1 = 2` 의 모순을 잡아 모든 부 목표 닫음.

자, 이 증명의 의미 — `Comp S1 R1 1 3` 가 가정될 때 그 안의 가설들이 자체 모순. 따라서 가정 자체가 성립 불가능. 곧 부정 명제 `¬ Comp S1 R1 1 3` 가 참.

이게 반례 (counterexample) 증명. 영어 "counterexample", 한국어 "반례". 진술 — "보편 명제 (예 합성이 가환)를 부정할 때 구체 인스턴스로 반박".

자, 두 example 종합 — `Comp R1 S1 1 3` 참, `¬ Comp S1 R1 1 3` 참. 곧 `Comp R1 S1 ≠ Comp S1 R1`. 합성이 비가환.

수학에서 — 합성의 비가환성을 반례 하나로 증명. Lean 4 에서도 같은 패턴.

학생들이 자주 묻는 의문 — "omega 가 1 = 2 같은 모순을 어떻게 처리하나요?"

답 — omega 의 결정 알고리즘이 산술 모순 탐지를 포함. `1 = 2` 같은 수치적으로 명백한 거짓 등식을 즉시 잡아냄. 결과 — 그 어떤 목표든 닫힘 (모순 가정에서 임의 결론).

또 의문 — "그러면 모든 모순이 omega 로 처리되나요?"

답 — 산술 모순만. 비산술적 모순은 다른 전술 (`contradiction`, `exact absurd ... ...` 등) 필요. 우리 예제는 모순이 산술적이라 omega.

## 블록 22 — 반사폐포와 대칭폐포 정의

```lean
variable {A : Type}

-- 반사폐포: R 에 항등관계를 합한다
def ReflClosure (R : A → A → Prop) : A → A → Prop :=
  fun a b => R a b ∨ a = b

-- 대칭폐포: R 에 역관계를 합한다
def SymmClosure (R : A → A → Prop) : A → A → Prop :=
  fun a b => R a b ∨ R b a
```

자, relation 의 마지막 절. 폐포 (closure) 두 가지.

먼저 `variable {A : Type}` — 다시 변수 선언.

### ReflClosure — 반사폐포

`def ReflClosure (R : A → A → Prop) : A → A → Prop := fun a b => R a b ∨ a = b`

`ReflClosure` — Reflexive Closure (반사폐포). 

함수 본체 `fun a b => R a b ∨ a = b` — 두 인수 a, b 에 대해 새 명제 반환.

`∨` — 새 기호. OR. 논리합. 영어 "or", 한국어 "또는". 키보드 `\or` 또는 `\vee`. 진술 — "두 명제 중 적어도 하나가 참".

`R a b ∨ a = b` — "(a, b) 가 원래 R 에 있거나, 아니면 a = b".

수학에서 — $r(R) = R \cup I_A = R \cup \{(a, a) \mid a \in A\}$. 곧 "원래 R 의 쌍 또는 대각선 쌍". Lean 4 의 `R a b ∨ a = b` 와 1:1 대응.

집합 합집합 (∪) ↔ 명제 OR (∨). 두 개념이 본질적으로 같음. 멤버쉽 술어를 통해 변환.

### SymmClosure — 대칭폐포

`def SymmClosure (R : A → A → Prop) : A → A → Prop := fun a b => R a b ∨ R b a`

`SymmClosure` — Symmetric Closure (대칭폐포).

함수 본체 `fun a b => R a b ∨ R b a` — "(a, b) 가 R 에 있거나, (b, a) 가 R 에 있음".

수학에서 — $s(R) = R \cup R^{-1}$. R 또는 역관계.

`R b a` 가 역관계 쌍의 표현. 인수 순서 변경.

자, 두 정의의 공통 구조 — 둘 다 OR 형태. "원래 R 의 쌍 또는 추가 쌍". 합집합의 명제 표현.

학생들이 자주 묻는 의문 — "그러면 추이폐포도 같은 방식으로 정의할 수 있나요?"

답 — 아니다. 더 복잡. 추이폐포는 무한 합집합 ($R \cup R^2 \cup R^3 \cup \cdots$) 이라 한 줄 정의 불가. 재귀적·귀납적 정의 필요.

```lean
inductive TransClosure (R : A → A → Prop) : A → A → Prop
  | base : ∀ a b, R a b → TransClosure R a b
  | step : ∀ a b c, TransClosure R a b → R b c → TransClosure R a c
```

`inductive` 라는 키워드로 시작하는 새 정의 방식. 두 생성자 `base` 와 `step` 으로 추이폐포를 점진적으로 구성. 자세한 건 후속 학습.

또 의문 — "Mathlib 에 표준 폐포 정의가 있나요?"

답 — 있다. `Relation.ReflGen`, `Relation.SymmGen`, `Relation.TransGen`, `Relation.EqvGen`. 우리 정의는 학습용 단순화 버전.

또 의문 — "OR 의 정확한 내부 작동은?"

답 — Lean 4 의 OR 가 유도형으로 정의.

```
inductive Or (p q : Prop) : Prop
  | inl : p → Or p q
  | inr : q → Or p q
```

두 생성자 — `inl` (왼쪽이 참), `inr` (오른쪽이 참). OR 의 증명은 둘 중 하나를 선택. 다음 블록에서 활용.

## 블록 23 — 반사폐포가 R 을 포함함

```lean
example (R : A → A → Prop) (a b : A) (h : R a b) :
    ReflClosure R a b := by
  left
  exact h
```

자, 짧지만 핵심적인 정리. "R 의 쌍은 반사폐포의 쌍이기도 하다."

`(h : R a b)` — 가설. (a, b) 가 R 에 속함.

`: ReflClosure R a b` — 결론. (a, b) 가 반사폐포에 속함.

`ReflClosure R a b` 의 정의 펼침 — `R a b ∨ a = b`. OR 형태.

`:= by left` —

`left` — 새 전술. 영어 단어 그대로 "왼쪽". 한국어 "왼쪽". 진술 — "OR 목표의 왼쪽 부분을 선택해 증명한다".

대조 — `right` — "오른쪽 선택".

InfoView 변화 — 전 — 목표 `R a b ∨ a = b`. 후 — 목표 `R a b`. OR 의 왼쪽만 남음.

`exact h` — 가설 h 가 정확히 `R a b`. exact 가 매칭. 닫힘.

자, 세 줄로 끝. 매우 간단한 증명.

학생들이 자주 묻는 의문 — "왜 left 인가요? right 도 시도해 봐야 하나요?"

답 — 두 가지 모두 가능하나 우리 가설로 닫을 수 있는 게 left.

만약 `right` 라면 — 목표가 `a = b`. 우리 가설 `h : R a b` 는 등식 `a = b` 가 아님. 닫을 도구 없음.

`left` — 목표 `R a b`. 가설 h 가 정확히 그것. 닫힘.

곧 가설을 보고 적절한 분기를 선택. 일반적인 OR 증명의 전략.

또 의문 — "그러면 모든 OR 증명이 left 또는 right 으로 시작하나요?"

답 — 그렇다. OR 의 증명은 항상 두 분기 중 하나를 선택. 곧 left 또는 right.

수학적 의미 — "(a, b) ∈ R" 이면 "(a, b) ∈ R 또는 a = b" — 자명한 함의. 합집합의 멤버쉽 정의.

또 한 가지 — "term 모드로 더 짧게 적을 수 있나요?"

답 — 가능. `Or.inl h` 가 left + exact 의 풀이 형태. 

```lean
example (R : A → A → Prop) (a b : A) (h : R a b) :
    ReflClosure R a b :=
  Or.inl h
```

세 줄이 한 줄. 더 압축적.

`Or.inl` — OR 의 왼쪽 생성자 함수. `Or.inl h` 가 "h 를 사용해 OR 의 왼쪽 분기를 증명".

다양한 방식이 가능. 상황에 따라 선택.

## 블록 24 — 대칭폐포가 대칭관계임

```lean
example (R : A → A → Prop) : Symm (SymmClosure R) := by
  intro a b h
  cases h with
  | inl hab =>
      right
      exact hab
  | inr hba =>
      left
      exact hba
```

자, 마지막 example. 대칭폐포가 정의대로 대칭관계임을 증명. 새 전술 `cases` 의 도입.

`Symm (SymmClosure R)` — 정의 펼침 — `∀ a b, SymmClosure R a b → SymmClosure R b a`.

`intro a b h` — 변수 둘, 가설 하나.

`h : SymmClosure R a b` — 정의 펼침 — `h : R a b ∨ R b a`. OR 형태의 가설.

목표 — `SymmClosure R b a` = `R b a ∨ R a b`. 또 OR. 주목 — 인수 순서가 바뀜.

`cases h with` — 새 전술.

`cases` — 영어 단어 그대로 "경우". 한국어 "경우 분석". 진술 — "유도형 가설을 그 생성자별로 분해".

OR 가설은 두 생성자 (`inl`, `inr`) 를 가지므로 `cases` 가 두 경우로 분해.

`| inl hab =>` — 첫 경우. 가설 h 가 `inl hab` 형태 (왼쪽 분기). hab 가 `R a b` 의 증명.

`| inr hba =>` — 둘째 경우. 가설 h 가 `inr hba` 형태 (오른쪽 분기). hba 가 `R b a` 의 증명.

`|` 가 패턴 매칭 표기. 함수형 언어의 표준. 영어 "pattern matching", 한국어 "패턴 매칭". OCaml, Haskell 같은 언어에서 자주 보는 표기.

자, 각 경우의 증명.

### inl 경우

가설 — `hab : R a b`. 

목표 — `R b a ∨ R a b`. 

자, 어느 분기를 선택? hab 가 `R a b`. 목표의 오른쪽 부분이 정확히 `R a b`. 따라서 `right` 선택.

`right` — OR 의 오른쪽 분기 선택. 목표가 `R a b` 로 변환.

`exact hab` — hab 가 정확히 `R a b`. 닫힘.

### inr 경우

가설 — `hba : R b a`.

목표 — `R b a ∨ R a b`.

목표의 왼쪽 부분이 `R b a`. hba 와 일치. `left` 선택.

`left` — 왼쪽 분기. 목표가 `R b a` 로.

`exact hba` — 닫힘.

자, 두 경우 모두 닫힘. 대칭폐포가 대칭관계임 증명 완료.

수학적 의미 — 대칭폐포의 정의가 `R ∪ R^{-1}`. 어떤 (a, b) 가 거기 있으면, (b, a) 도 거기 있다 (왼쪽이었으면 오른쪽으로, 오른쪽이었으면 왼쪽으로). 정확히 대칭성.

학생들이 자주 묻는 의문 — "cases 와 obtain 의 차이는?"

답 — 기능은 비슷하지만 cases 가 더 명시적. cases 는 각 경우의 이름을 `| inl ... | inr ...` 로 명명. obtain 은 `obtain hab | hba := h` 같이 더 짧게도 가능.

`cases h with | inl hab => ... | inr hba => ...` 가 가독성 좋음. 각 경우가 무엇인지 즉시 보임.

또 의문 — "왜 inl, inr 인가요?"

답 — injection left, injection right 의 줄임. Or 의 두 생성자 이름. 유도형의 표준 접두사. 다른 타입에서도 비슷 — Sum 타입의 inl, inr.

또 한 가지 — "cases ... with 외에 다른 표기는?"

답 — `match h with | inl hab => ... | inr hba => ...` 같은 직접 패턴 매칭도 가능. cases 가 전술 모드의 자연스러운 표현.

자, 큰 그림. 우리 example 의 패턴 — OR 가설을 cases 로 분해, 각 경우에서 OR 목표의 적절한 분기를 left/right 으로 선택, 가설을 exact 로 매칭. 

이게 OR 가설과 OR 목표를 다루는 표준 패턴. relation 의 폐포 정리들에서 자주 등장.

| `constructor` | 합접·동치 목표 분해 |
| `·` | 부 목표 시작 |
| `cases h with | inl ... | inr ...` | OR 가설 분해 |
| `left`, `right` | OR 목표 분기 선택 |
| `exact 항` | 정확한 증명 항 제공 |
| `unfold 정의 at` | 정의 펼치기 |
| `omega` | 선형 정수 산술 자동 |

### 자주 쓰는 점 표기

| 표기 | 의미 |
|---|---|
| `h.symm` | `Eq.symm h` |
| `h.trans h'` | `Eq.trans h h'` |
| `h.mp` | iff 의 정방향 |
| `h.mpr` | iff 의 역방향 |
